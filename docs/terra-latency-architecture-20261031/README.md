# Terra 복원 품질·대기 시간: 다음 구조 권고

2026-10-31 · Astra · 새 모델 호출 0 / 제품 변경 0

**권고는 low 판독이 끝날 때까지 기다리는 자동 연쇄를 기본으로 만들지 않고, 촬영 종료 때 읽을 범위와 강도를 고정해 독립 작업을 바로 시작하는 것이다.** 복원 중심의 첫 구현 후보는 **전체 high 1회, 사전에 필요한 부분이 정해져 있을 때만 부분 high 1회를 동시에 실행**하는 형태다. 둘 다 항상 호출하는 정책은 권고하지 않는다. 기존 low 기본값을 이번 연구로 일괄 바꾸지도 않는다. 먼저 요청별 high 경로와 작은 결합 교정을 구현해 기존 low 경로와 비교한다.

이 선택은 high가 항상 정확하거나 빠르다는 판단이 아니다. 전체 low + 부분 high를 새로 오프라인 조합하니 카르카손은 12/16개로 전체 high의 16/16개보다 부족했다. 반면 사그라다 숫자는 low 단독도 19/20개였다. **현재 자료로는 품질과 시간을 동시에 지배하는 단일 effort 정책을 고를 수 없다.** 독립 작업의 선행 대기를 없애는 구조는 선택할 수 있지만, 자동 강도·ROI 선택기의 품질은 미확인이다.

초기 서비스의 동시 사용량이 적다는 가정이다. 요청당 최대 6단위와 provider 한도는 유지한다. 여러 사용자가 겹쳤을 때의 처리량·429 발생률은 측정하지 않았으며, 새 전역 큐를 선행 조건으로 추가하지 않는다.

## 2. 품질: 모름 보충, 처음부터 미검출, 오독을 구분

기존 12개 응답은 3개 개발 사진의 단회 조건이다. 기준은 출력 전 고정한 **AI 부분 참조**이며 사람 인증·전체 사진 정답이 아니다. A=전체 low, B=전체 high, C=같은 원본 crop low, D=같은 crop high. [기존 9회 독립 분석](../terra-quality-iteration-20261030/independent-high-review.md), [추가 3회 독립 분석](../terra-quality-iteration-20261030/independent-crop-high-review.md).

| 선택한 부분 기준 | A | B | A+D 현재 코드 재생 — 이번 분석 | B+D 기존 독립 재생 |
|---|---|---|---|---|
| 카르카손 개별 물체 | 10/16 | 16/16 | **12/16** | 16/16 |
| 사그라다 개별 물체 / 숫자 | 20/21; 정19·오1 | 21/21; 정17·오1·모름2 | **20/21; 정19·오1** | 21/21; 정19·오1 |
| 티켓 투 라이드 개별 기물·색 | 25/25 | 25/25 | 25/25 | 25/25 |

**VERIFIED_OFFLINE:** 이번 A+D 재생은 기존 원응답을 그대로 사용했다. raw 48/45/93개 보존, 순서 역전·중복 재전달·JSON 왕복 동일, 부분 참조로 대응 가능한 연결에서 오연결 0. 최종 편집 객체·선택 기준 밖 전체 precision은 미평가다. [replay-ad.mts](replay-ad.mts), [offline-ad-replay.json](offline-ad-replay.json). 이 함수 재생은 mixed-effort job의 요청/commit 검사를 통과했다는 뜻이 아니다. 현재 단일 reader pin으로는 A+D 제품 실행 계약을 별도로 연결해야 한다.

- **처음부터 미검출·묶음:** 카르카손 high의 추가 6개는 중간 신뢰 타일 경계의 개별화다. low가 읽지 않은 물체에는 `unknown` 행조차 없을 수 있어, 모름 수만 보고 보강을 발행하면 누락을 놓친다. 재고·시작 배치 수량으로 채우지 않는다.
- **모름 보충:** B+D 사그라다는 서로 다른 위치의 모름을 보충했다. high-confidence 18개는 정17·오1로 A/B와 같다. 두 응답이 동의해도 공통 오독 1개가 남는다.
- **결합 손실:** A+C/B+C에서는 작은 crop을 우선한 `focused()` 규칙 때문에 전체의 맞는 숫자 3개가 틀린 값으로 교체됐다. 작은 ROI와 같은 픽셀 밀도는 정답 우위가 아니다. 이번 A+D/B+D의 숫자 충돌 0은 이 결함이 해결됐다는 증거가 아니다.
- **평가 해석:** 카르카손 기하 중복 후보 7건은 정상 층 겹침·인접 타일과 거친 참조 경계가 섞여 있다. 실중복 7건으로 세지 않는다. 티켓의 묶음 0/8은 이미 회수한 개별 기물의 대체 표현이다. 같은 원본 crop을 다른 시점·독립 표본으로 세지 않는다.

## 3. 시간: 실제 기록과 겹쳐 계산한 시나리오

`providerMs`는 네트워크 요청부터 완전 응답 수신까지이며 모델 연산만의 시간이 아니다. 현재 cloud 완료 메타의 `providerMs` 합계도 병렬 wall이 아니다. 원기록의 `providerMs`로 아래를 계산했다. [timing-analysis.py](timing-analysis.py), [timing-analysis.json](timing-analysis.json).

| 사진 | A / B / D **기존 개별 실측** | A→D 순차 / A∥D 동시 **계산** | B→D 순차 / B∥D 동시 **계산** | B∥D 첫 부분 결과 **계산** |
|---|---:|---:|---:|---:|
| 카르카손 | 24.00 / 174.38 / 96.91초 | 120.92 / 96.91초 | 271.29 / 174.38초 | 96.91초 |
| 사그라다 | 32.91 / 79.07 / 43.21초 | 76.12 / 43.21초 | 122.28 / 79.07초 | 43.21초 |
| 티켓 투 라이드 | 70.66 / 82.24 / 50.10초 | 120.75 / 70.66초 | 132.34 / 82.24초 | 50.10초 |

**INFERRED, 새 병렬 실측 아님:** 각 호출의 시간이 그대로 유지되고 즉시 함께 출발할 때 순차는 합, 동시는 최댓값이다. min/max는 통계적 신뢰구간이나 보장 상·하한이 아니다. provider 부하·병렬 간섭·출력 변동·429는 포함하지 않았다. 전체 high가 반드시 필요하다면 low→전체 high의 선행 low 24~71초는 생략할 수 있다. 하지만 **카르카손 B∥D 174초는 A→D 121초보다도 길다.** 서로 다른 품질 조건을 비교해 병렬화가 항상 빨라졌다고 말할 수 없다.

실제 사용자 종단 경로는 다음이다.

```text
촬영 중 ticket/PUT 중첩
  → 종료 뒤 남은 PUT → 배치 등록 → job 고정
  → 원본 읽기·crop 준비 → 독립 요청 동시 시작
  → 먼저 끝난 단위: 사진 관측 미리보기
  → 모든 단위 완료/실패: 결합·scope/CAS 확인·최종 저장
  → 사용자가 필요한 곳 정정·저장·재열기
```

`T첫표시 = 종료후전송/등록/준비 + min(요청시작차+응답시간) + 폴링/렌더`

`T최종편집 = 종료후전송/등록/준비 + max(요청시작차+응답시간) + 결합/commit/폴링`

`T복원가능저장 = T최종편집 + 필요한 사람 검토·정정·저장`이며 마지막 항은 **UNKNOWN**이다. 이번 로컬 A+D 결합 CPU는 3.9~10.3ms였다. cloud I/O/모바일 렌더 성능으로 일반화하지 않는다. 이전 Gemini 실행기의 업로드 45.5초를 현재 Terra 기록에 더하지 않는다. 촬영 종료 시 업로드가 얼마나 남는지도 이번 자료에는 없다.

현재 `runHostedScan`은 모든 입력 이미지 읽기와 단위 준비가 끝나야 dispatch한다. 느린 원격 detail 한 장이 첫 요청을 지연할 가능성은 있지만 이번 Terra 실행 기록에는 그 크기가 없다. 이미 있는 이미지 캐시·동시 읽기를 유지하고 먼저 이 대기를 재본다. 그것이 중요하면 **고정된 전체 계획은 유지한 채 준비 완료 단위부터 claim/dispatch**하는 작은 후속 단계로 분리한다. 원본 등록 전 발행·미고정 crop 재생성·동일 요청 재발행으로 우회하지 않는다.

출력 토큰(추론 포함)은 A 세 건 9,586 → B 29,361, 그중 reasoning은 330 → 10,379였다. high 지연의 상당 부분이 추론·출력과 관련 있다는 근거지만 정확한 단계별 연산 시간을 분리한 측정은 아니다. 출력 상한을 무작정 줄이면 중단 응답을 만들 수 있어 첫 변경에서 유지한다. 일반적인 병렬·출력량 원칙은 [OpenAI 지연 최적화 문서](https://developers.openai.com/api/docs/guides/latency-optimization)에 부합하지만 그 문서의 절감 수치를 KeepBoard에 적용하지 않는다.

## 4. 현실적인 대안 네 가지

| 구조 | 품질·대기·비용 판단 | 채택 여부 |
|---|---|---|
| 전체 low → 부족한 곳 high | 필요 없으면 high 비용 절약. 그러나 명시 모름만으로 실제 누락 판별 불가, 보강 시 시간이 합산됨. `observed`/confidence가 정답 검증은 아님 | 예외적 후속 작업. 기본 자동 연쇄로 도입하지 않음 |
| **전체 high 즉시 + 사전 선택 부분 high 병렬** | whole 범위 유지. B+D 부분 기준이 가장 많이 회수됐으나 2/3사진에서 detail 추가 이득 없음. high 자체 지연은 남음 | **복원 중심 첫 구현·비교 후보. 부분은 선택적이고 global low 기본 변경은 별도 결과로 판단** |
| 전체 low + 부분 high 병렬 | A+D는 계산상 43~97초, 비용도 낮음. 카르카손 4타일과 사그라다 1판이 B+D 대비 미회수. 잘못된 anchor를 자동 정답으로 보지 않아야 함 | 빠른 대안. 충분한 복원 기본값이라는 근거 없음. mixed-profile 구현은 첫 slice 뒤로 미룸 |
| 한 요청에 overview + 여러 detail | 공동 문맥과 요청 overhead 감소 가능성이 있다. 반면 모든 이미지·긴 출력이 한 요청에 묶이고 부분 실패·출처 index 계약이 바뀐다. 여러 이미지는 각각 토큰으로 과금되며 한 요청이 된다고 이미지 비용이 사라지지 않는다 | 미검증. 현재 1-image reader를 고치는 비용보다 이득이 크다는 근거가 없어 보류 |

기존 요율로 환산한 B 단독 / B+D / A+D 비용은 각각 카르카손 **$0.079789 / $0.123806 / $0.054831**, 사그라다 **$0.036036 / $0.055555 / $0.034455**, 티켓 **$0.037808 / $0.060546 / $0.051746**다. 새 견적·실청구가 아니다. 세 사진의 B+D 합은 $0.23990675, A+D는 $0.14103175다. 병렬은 같은 요청 집합의 토큰을 줄이지 않는다. 상세 high가 무용했던 두 사례도 숨기지 않는다.

**적응/추측 발행의 선택:** whole 결과가 필요한 ROI 선택이면 그 요청은 정말 종속적이므로 동시에 보낼 수 없다. 이미 촬영 구역으로 정해진 detail만 미리 발행한다. whole 시작 후 임의 지연 d를 두면 계산 완료시간은 `max(Twhole, d+Tdetail)`이다. 발행 전에 불필요함을 알아낼 때만 그 호출 전체 비용을 확실히 피할 수 있다. 현재는 이를 판정하는 로컬 충분성 검사·보정된 confidence가 없으므로 타이머 기반 추측/취소 정책을 추가하지 않는다.

**더 잘게 나누면 빨라지는가:** 균형 잡힌 독립 crop들은 가장 긴 출력 요청을 줄일 가능성이 있지만, 원본 문맥·경계 물체·중복·개별/묶음 관계를 잃고 토큰이 중복될 수 있다. 현재 3사진은 한 crop씩이라 최적 분할 수를 찾은 실험이 아니다. 고정 4분할·전체 high 제거를 도입하지 않는다. 이미 알려진 물리 구역이 있는 경우에만 후속 granularity 비교 대상으로 둔다.

## 5. 가장 작은 구현 경계

1. **요청별 판독 강도 고정:** 현재 job은 reader 한 개라 첫 버전은 `low` 또는 `high` 한 강도로 whole와 선택 detail을 통일한다. identity→body→receipt→재접속/commit에 같은 값을 전달한다. 미지정·과거 job은 low. native Catan도 같은 경로를 통과하되 별도 품질 합격으로 보지 않는다. 별도 low 탐색 호출, 항상 crop 생성, 응답 후 무한 계획 확장은 추가하지 않는다.
2. **관측 간 알려진 값 충돌 교정:** 작은 crop이라는 이유만으로 known 값을 바꾸지 않는다. 사용자값 우선, 나머지는 기존 잠정 선택/안정된 anchor와 대안을 남긴다. 한쪽 모름 보충·정상 물체·원문/출처·group refinement는 유지한다. anchor 역시 틀릴 수 있으므로 선택 근거를 보존하고 직접 정정 가능하게 둔다.
3. **이미 있는 병렬·진행·저장 재사용:** source crop 변환이 있는 입력만 자동 정합, 다른 각도는 기존 미연결 관측으로 보존한다. owner/epoch/정지 상태·판본을 넘지 않는다. 최종 쓰기는 기존 한 번의 CAS로 유지한다. 중간 저장을 추가해 스스로 scope revision을 바꾸지 않는다.

ROI는 우선 **이미 등록된 `sourceRegion`/사용자가 제공한 같은 상태의 부분 입력**만 이용한다. 로컬 선별은 흐림·중복 제거에 사용하고, 게임팩 영역·종류·속성은 읽을 범위를 좁히는 참고로 쓴다. 사진에 없는 물체·숫자·소유·현재 배치의 정답으로 쓰지 않는다. 사전 ROI를 자동으로 잘 고르는 능력은 아직 없으며, 임의 사분할이나 기존 정답 박스로 대체하지 않는다. 별도 각도 사진은 가까이 찍혀도 등록 crop과 같은 기하 증거가 아니다.

상세 파일·수용 검사·새 사진 비교는 [implementation-cards.md](implementation-cards.md)에 있다. 한 기존 Sol이 연결된 backend/shared slice를 맡고 UI 소유권은 감독이 분리한다. 새 의존성·큐·정합 엔진은 필요하지 않다.

## 6. 진행 표시·취소·실패의 한계

- **SSE:** [공식 스트리밍 문서](https://developers.openai.com/api/docs/guides/streaming-responses)는 text delta와 완료 이벤트를 제공한다. 토큰이 왔다는 사실은 개별 관측 JSON·정체·좌표가 유효함을 뜻하지 않는다. 현재 decoder는 완료 응답만 받는다. 기존 단위 완료 미리보기를 우선 재사용한다. 토큰 스트리밍이 high의 생각 시간을 줄인다는 근거는 없다.
- **취소:** [공식 background 문서](https://developers.openai.com/api/docs/guides/background)에 background cancel과 동기 연결 종료 취소가 있으나, 현재 앱의 비동기 job은 provider background가 아니다. 브라우저 이탈은 서버 fetch 취소와 다르다. 이미 발행한 호출의 과금 환불/절감량도 미확인이다. background는 현재 문서상 첫 토큰 지연이 더 높아 지연 개선 목적으로 옮기지 않는다.
- **예산·429:** 실행 전 전체 선택 단위 비용을 예약하고 기존 최대 6 입력 및 per-unit claim을 유지한다. 첫 slice는 전체 1 + 선택 detail 1의 작은 계획으로 비교하되 전역 동시 수를 임의로 2로 되돌리는 변경은 아니다. 요청 하나가 실패하면 성공 단위는 남기고 해당 실패를 표시한다. 자동 유료 retry·다른 모델 대체·동일 claim 재발행은 0. 이미 병렬 발행된 요청은 실패를 안 시점에 소급 취소할 수 없다.
- **사진 한계:** 작은 글자·회전·공간 위치·계수의 한계는 [공식 vision 문서](https://developers.openai.com/api/docs/guides/images-vision)에 명시돼 있다. crop은 새 광학 정보를 만드는 것이 아니다. 보이지 않는 상태·숫자는 모름/사진 보존/선택 정정으로 남기며 두 응답 일치를 정답 인증으로 쓰지 않는다.

공식 문서 열람일 **2026-10-31**. 이 연구는 새 실사진 실험·HTTP/UI 테스트·제품 변경을 수행하지 않았다. **아직 미확인:** 미사용 사진 일반화, ROI 선택 효율, 사람 정정 시간, 실제 업로드 포함 종단 대기, 현재 배포 연결, 동시 사용자 부하, 실청구. 30초·120게임 정확도·완벽 복원을 보장하지 않는다.

기계 근거: [evidence.json](evidence.json), [verification.json](verification.json). 해시·링크·문법 확인은 실물 정확도 시험과 구별한다.
