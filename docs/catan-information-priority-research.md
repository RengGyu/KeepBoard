# 카탄 기본판: 핵심 화면, 플레이어 보유 상태, 항구·교역 구현 명세

조사일: 2026-10-20. 범위: 기본판 3–4인 저장·확인·재개. 제품 소스는 변경하지 않았다.

## 1. 구현자가 먼저 가져갈 결론

**RECOMMENDATION**

1. 첫 화면은 **현재 차례·남은 처리 → 공용 판과 항구 → 플레이어별 공개 상태 → 지금 필요한 질문/주요 버튼** 순서로 줄인다. 전체 구성물, 근거 사진 목록, 상세 보관 조건, 전체 필드, JSON은 기본 닫힌 **“더 보기 +”**로 옮긴다. 현재 밝은 색상과 구성물 그림은 유지한다.
2. 플레이어의 “재산”은 **자원, 개발 카드, 설치물/남은 말, 점수, 특수 타이틀, 이용 가능한 교역비율**로 구분한다. 임의의 총재산 점수로 합산하지 않는다. `0`, 미확인, 실물 보관으로 해결한 상태를 다르게 표시한다.
3. **항구는 내륙 19칸 밖의 해안 요소**다. 해안 변 하나와 그 양 끝 꼭짓점을 연결하고, 자기 건물이 닿는 항구에서 교역비율을 도출한다. 공용 그림·사진 인식·편집·플레이어 요약·재개 비교가 같은 데이터를 사용해야 한다.
4. 사용자에게 제공할 최소 교역 기능은 **줄 자원/받을 자원 선택 → 은행·항구 비율과 조건 안내 → 중단된 교환의 실제 진행 기록**이다. 자동으로 손패를 소비하는 전체 플레이 엔진은 만들지 않는다.
5. 현 팩은 `Base Game (2020 rules)`다. 신규 6판 프로필의 행동 단계와 기존 저장본의 거래/건설 단계를 구별한다. 배치 정정, 규칙 안내, 실제 게임 행동은 서로 다른 동작으로 유지한다.

## 2. 확인 범위와 공식 근거

**VERIFIED:** 현재 코드와 저장된 화면 이미지를 함께 확인했다. **UNCLEAR:** 열린 브라우저의 실제 세션은 개인 자료 열람 가능성을 이유로 자동 승인 검토가 접근을 거절했다. 해당 세션을 우회 열람하지 않았다. 따라서 실행 중 세션의 최신 픽셀 상태는 확인하지 못했고, 위 저장 화면과 아래 현재 코드가 화면 판단의 근거다.

| 마을 1점, 도시 2점, 승점 카드 1점; 본인 차례 10점 이상으로 종료 | R20 p.14; R6 p.10 | 공개 계산 점수와 소유자 총승점 분리. 숨은 승점 미확인일 때 자동 종료 금지 |
| 사막은 숫자/생산 없음. 18숫자, 7 없음 | R20 p.10,13 | 불일치는 표시하되 실제 사진 정정/저장을 막는 근거로 남용하지 않음 |
| 기본 공급량: 각 색 도로15/마을5/도시4, 자원 각19, 개발25 | R20 p.2–3 | 전체 구성물은 더 보기. 분실/부분 관측에서는 상자 정원−관측값을 확정 재고로 취급하지 않음 |

더 보기의 건설 참고표에는 도로=`벽돌1+목재1`, 마을=`벽돌1+목재1+양모1+곡물1`, 도시 업그레이드=`곡물2+광석3`, 개발 카드=`양모1+곡물1+광석1`을 둔다(R20 p.4–5). 저장판의 도시를 정정할 때 이 비용을 차감하지 않는다. 구성물 상세에는 개발 카드 `기사14/도로건설2/발견·풍년2/독점2/승점5`를 표준 정원으로 표시한다(R6 p.3). 정원은 실제 남은 덱의 정체를 추론하는 근거가 아니다.

**판본 선택:** R6 p.6–7은 생산→행동이며 거래/건설 순서를 자유롭게 섞는다. R20 p.4는 분리하고 p.6에서 통합을 권장 변형으로 제시한다. 항구를 지은 턴의 즉시 이용도 이 선택에 따른다(FAQ “May I trade via a harbor right after building it?”). 신규 팩은 `rulesProfile='base-6e-2025'`, 기존 팩은 `base-2020`을 유지하고 `tradeBuildMode='combined'|'separate'|null`을 기록한다. 기존 저장본을 새 기본값으로 덮지 않는다. 언어만 보고 판본·프레임 배치를 확정하지 않는다.

**범위:** 선박, 해적, 상품, 도시와 기사, 5–6인 특별 행동은 포함하지 않는다. 도둑의 저득점 보호 같은 선택 변형도 기본으로 켜지 않는다.

## 5. 화면 우선순위

| 목적 | 기본으로 보일 내용 | “더 보기 +” 안의 내용 |
|---|---|---|
| 스캔/확인 | 첫 촬영 버튼 또는 판독 그림, 후보/확정 표시, 가장 높은 우선순위의 미해결 질문, 선택한 말의 종류/소유자/위치 정정 | 추가 촬영 지시, 전체 원본·후보·구성물 목록, 사진 영역 좌표, 전체 필드, JSON |
| 저장 준비 | 현재 사람·단계·남은 처리, 공용 판/항구 확인 상태, 플레이어 공개 요약, 비공개 묶음 준비 여부, 저장 버튼 | 개별 보관 조건 전체, 이미 완료한 항목, 기록 근거·판본 설명·구성물 총목록 |
| 이어하기 | **다음에 할 실제 절차**, 저장 시 차례/단계, 복원할 판과 항구, 아직 복원하지 않은 묶음, 관련 차이, 이 턴 계속하기 | 전체 브리핑, 모든 원본/비교 값, 완료된 복원, 상세 목록, 다음 턴 기록 동작 |
| 소유자 화면 | 내 자원 종류별 수/자원 총수, 기존·신규 개발 카드 요약, 내 개인승점, 내게 남은 처리 | 개별 카드/근거/보관 위치, 선택 메모, 전체 원시 기록 |

“더 보기 +”는 정보의 표시 우선순위만 바꾼다. 현재 처리에 꼭 필요한 필드를 접어서 해결된 것처럼 만들지 않는다. 예를 들어 7의 버리기 잔여량은 첫 화면에 올리고, 평소에는 숨긴다. 오류/경고는 보드 위 `확인할 배치 N개`로 요약하고 해당 대상을 누르면 자세히 연다. 복구 가능한 미확인 상태 저장은 유지한다.

현재 `SceneWorkspace`·`PhotoTargetBrowser`·`EvidenceStrip`의 중복 노출부터 줄이고, 기존 `RecordedFields`의 접기를 활용한다. 보드 정정용 “저장”과 세션 “이 판 저장하기”는 `배치 정정 저장` / `판 저장`처럼 구별한다.

### 질문 활성 조건

| 필드/입력 | 켜지는 때 | 표시 범위/처리 |
|---|---|---|
| 현재 사람·규칙 프로필·진행 단계 | 미확인일 때 | 공용. 사람은 자유 텍스트 대신 실제 player ID 선택 |
| 주사위 합계 | 생산/7 처리가 남았고 이번 굴림이 필요한 때 | 공용. 완료된 과거 굴림은 상세 기록; 굴리기 전에는 묻지 않음 |
| 생산 완료·남은 지급 | 생산 중 | 공용. 부족한 자원 종류/받을 사람만 추가 입력 |
| 버리기 남은 수 | 7 처리 중이며 해당 사람의 완료가 미확인 | 개인 입력; 공용은 진행 여부/확인된 남은 수만. 현재 손패를 다시 절반으로 계산하지 않음 |
| 도둑 원인·목적지·훔치기·복귀 단계 | 7 또는 기사 효과 진행 중 | 공용. `victim='none'`와 미확인을 구별; 훔친 자원 정체는 공용 필드에 요구하지 않음 |
| 행동 개발 카드 사용 여부 | 본인 턴의 재개에 영향을 주며 미확인 | 굴리기 전도 포함. 한 번 사용한 사실을 재개 시 초기화하지 않음 |
| 이번 턴 구매 카드 세부 | 구매가 확인된 소유자 | 소유자 전용. 개수·종류를 모르더라도 새 카드 묶음을 따로 보존 가능 |
| 개발 카드 효과 세부 | 해당 효과 처리 중 | 도로 남은 개수/두 자원 중 남은 지급/독점 수금 등 실제 남은 작업만 |
| 초기 배치 순서·단계 | 초기 배치 중 | 공용. 일반 거래/건설 질문 대신 배치·초기 자원 질문 |
| 교역 도우미 | 사용자가 열거나 거래 처리 중 | 평소 플레이어 행에는 비율 요약만. 단계/차례 미확인은 계산값과 실행 가능을 구별 |
| 승리/종료 확인 | 본인 총승점 확인 또는 종료 기록 요청 | 개인 승점은 본인에게만. 공용 종료는 명시적으로 확인한 결과만 |

활성 조건의 선행 상태가 모르면 선행 질문부터 올린다. 미확인을 `false`나 “처리 완료”로 취급하지 않는다.

**필드 변경안:** `turn.phase`는 기존 값을 읽되 신규 팩에서 `setup`, `action`, `finished`를 추가한다. `action`은 통합 프로필에, `trade/build`는 분리 프로필에 사용한다. 기존 `build`를 사용자 확인 없이 `action`으로 바꾸지 않는다. `robber.cause='seven'|'knight'|null`, `turn.returnPhase`로 효과 전 단계를 보존한다. `setup.round=1|2|null`, `setup.step='settlement'|'road'|'starting_resources'|null`, `setup.startingResourcesResolvedByPlayer`는 초기 배치에서만 묻는다. `game.status='playing'|'finished'|null`, `game.winnerPlayerId`는 확인된 종료 기록에 사용한다. 기본판은 좌석 순서를 따라가므로 `session.players`가 실제 차례 순서인지 먼저 확인하고, 단순 색상 정렬에서 다음 사람을 추정하지 않는다.

## 6. 플레이어 보유 상태 계약

### 표시할 항목

| 항목 | 공용 요약 | 소유자 상세 | 정확성 조건 |
|---|---|---|---|
| 자원 | 자원 손패 총수 | `lumber/brick/wool/grain/ore` 각각의 정수 수량 | 총수 공개 의무는 FAQ Resource Cards. 종류별 미확인과 0 구별 |
| 개발 카드 | 확인된 미사용 카드 장수만 선택 표시; 공개 기사 수·사용 제한 | 미사용 전체, 이번 턴 구매분, 사용한 카드/효과, 비공개 승점 | 뒷면에서 종류·구매 시점 추정 금지. 장수 공개 표시는 확인 근거가 있을 때만 |
| 설치물 | 도로/마을/도시 개수 | 같은 공개 정보와 개별 위치 | 공용 확정 장면의 소유자·수량만 집계. 여러 장면/여러 사진의 중복 합산 금지 |
| 남은 말 | 도로/마을/도시 재고 | 개별 묶음·보관 위치 | 직접 확인 재고 우선. 완전한 배치와 기본 공급량이 확인된 경우에만 계산값 제공 |
| 점수 | 공개 건물·확인된 타이틀의 점수 | 공개 점수 + 비공개 승점 카드 | `확인분 5점`과 `공개 5점 확정`을 구별. 도로 개수 자체는 점수 아님 |
| 타이틀 | 실제 보유자, 공개 기사 수, 확인된 최장 길이 | 기준 충족 이유/미확인 사유 | 기준 충족과 보유 확정을 구별. 동률/과거 보유 불명은 확인 요청 |
| 교역 | 자원별 확인된 비율, 이용 항구 표시 | 내 자원으로 교환 수량 미리보기 | 항구/건물 미확인이면 “확인된 비율”로 표현; 최선 비율 확정 금지 |

**RECOMMENDATION — 최소 타입 방향**

```ts
type Resource = 'lumber' | 'brick' | 'wool' | 'grain' | 'ore';
type Counts<K extends string> = Record<K, number | null>; // 0은 확인한 없음
type Dev = 'knight' | 'road-building' | 'year-of-plenty' | 'monopoly' | 'victory-point';

// FieldDefinition 추가: scope는 소유 대상을, visibility는 표시 범위를 뜻한다.
visibility?: 'public' | 'owner'; // 생략 시 기존 public/player 동작 유지
lifetime?: 'session' | 'turn';  // UI group과 초기화 정책 분리
ui?: {
  level: 'primary' | 'detail';
  order: number;
  showWhen?: Condition;
  editor?: 'resource-counts' | 'development-counts' | 'player' | 'default';
};
```

- `player.resources.counts`: 개인 `Counts<Resource>`. `player.resources.total`: 개인에 귀속되지만 공개 표시 가능. 종류별 값 전부가 확인된 때에만 자동 합산한다. 별도 확인 총수와 충돌하면 둘 다 근거를 남기고 확인 요청.
- `player.development.handCounts`: **미사용 전체**를 의미하도록 신규 팩에서 명확히 정의한다. 기존 팩은 “기존 카드” 의미였으므로 신규 구매분을 무조건 더하는 마이그레이션은 금지한다.
- 신규 `player.development.purchaseBatches`: `{ purchasedTurnId, counts: Counts<Dev>, preservationId? }[]`. 이미 전체 손패에 포함된 부분집합이며 합계에 다시 더하지 않는다. 정체 미기록인 실물 묶음도 유지한다. 다음 턴 변경 시 **사용 제한만 만료**, 카드 보유 사실은 삭제하지 않는다. 기존/신규 묶음을 합치는 시점은 사용자 확인으로 기록한다.
- 구매 묶음은 현재 미사용 카드와 실물 보관을 구별하는 용도다. 구별할 필요가 끝난 묶음은 전체 손패에 포함된 상태로 정리하고 과거 구매 이력을 무한히 누적하지 않는다. 원래 중단 시점의 구분은 저장본에 남긴다.
- `player.development.knightsPlayed`, `player.road.longestContinuousSegments`: 플레이어 귀속 + 공개 표시. 공개 사진에서 명확히 식별한 소유자별 후보를 허용한다. 진보 폐기 카드는 공용 폐기 묶음으로 보존할 수 있고, 과거 사용자별 이력은 필수가 아니다.
- 신규 `player.pieces.remaining`, `player.score.public`, `player.score.total`은 각각 수량/공개 도출/개인 도출. 도출값에는 `complete/partial/unknown/conflict`, 근거 assertion ID를 붙인다. 이미 `Assertion.basis`, 상태, 원본 연결이 있으므로 원본 데이터를 별도 복제하지 않는다.
- 공개 계산은 확정 건물의 `마을 + 2×도시 + 타이틀별 2`로 구성한다. 업그레이드한 도시에 이전 마을 점수를 중복 더하지 않는다. 숨은 승점 카드는 소유자 합계에만 추가한다.
- 배열에 없는 플레이어/카드 종류를 0으로 채우지 않는다. 실물 묶음 보관은 “복원 방법 확보”이지 “정확한 디지털 수량 확보”가 아니다.
- 현재 소유자 탭은 화면 구분이며 본인 인증을 입증하는 기능은 아니다. 이번 구현은 공용 요약/근거/차이 목록에 비공개 종류·승점이 섞이지 않게 표시 계약을 지켜야 한다. 별도 계정·인증 체계 신설은 이 명세의 범위가 아니다.

`visibility`를 추가하면 `SessionWorkspace`의 단순 owner 필터, `Fields`, `PhotoTargets`, 브리핑/차이 목록을 같은 표시 선택자로 통일한다. 개인 질문은 소유자에게 두되 공개 가능한 결과만 공용 행에 표시한다. 공개 사진→플레이어 귀속 공개 필드의 인식에서는 `server/ai/index.ts:116–117`의 현재 “사진 소유자=필드 소유자” 가정을 조정해야 한다. 미확인 소유자는 만들어내지 않는다.

## 7. 바다·항구·교역 계약

### 공식 근거와 배치 차이

**VERIFIED:** 기본판 항구는 9개이며, 일반 3:1 네 곳과 자원별 2:1 다섯 곳이다(R20 p.2·3·9; 일반 항구 수는 전체 9−자원별 5와 배치 그림으로 확인). 해당 항구의 마을/도시가 있어야 이용한다. 은행 4:1은 항구 없이 이용한다. 자원별 항구는 **내는 자원**을 지정한다(R20 p.9; R6 p.7).

R20 p.12–13은 프레임 순서 변경/항구 조각 재배치를, R6 p.11은 프레임 섞기를 허용한다. 그러므로 “북서쪽은 항상 목재항구” 같은 지도는 인식 기본값이 될 수 없다. 외관·한국어/영어만으로 실제 프레임 배치나 판본을 단정하지 않는다. 기본 배치 템플릿은 사용자가 해당 판본·배치를 선택한 경우에만 생성하며, 관측 근거와 구분한다.

### 기하 계약

**VERIFIED:** `shared/scene.ts`의 순수 topology를 직접 읽어 실행한 결과 `19 hex / 54 vertex / 72 edge`, 그중 `edge.hexIds.length===1`인 **해안 변 30개, 해안 꼭짓점 30개**다. 항구 접점 계산에 새 내륙 칸을 추가할 필요가 없다.

**RECOMMENDATION:** `kind='harbor'`를 추가하고 장면 버전을 2로 명시한다. v1/레거시 읽기는 유지한다. 신규 계약의 예시는 설명용이며 실제 판 관측값이 아니다.

```ts
// SceneComponent의 공통 id/quantity/location/evidenceId/region/note는 유지.
{
  id: 'harbor-1',
  kind: 'harbor',
  variant: 'lumber',       // generic | Resource | null
  ratio: 2,                // 2 | 3 | null; 비율만 보이고 자원은 모를 수 있음
  ownerId: null,           // 항구 자체의 플레이어 소유를 저장하지 않음
  quantity: 1,
  location: { type: 'edge', id: 'r1c1.NW' },
  evidenceId: null,
  region: null
}
// 이 변의 두 이용 접점은 실제 topology에서 ['r1c1.NW','r1c1.N'].
// endpoint IDs는 중복 저장하지 않고 edge.vertexIds로 계산.
```

- 유효한 항구 앵커는 해안 변. 내륙 변에 신규 항구를 놓는 편집은 거부한다. 위치를 못 읽으면 `edge/null` 또는 `unplaced/null`로 보존하고 항구 접근 계산에서는 제외한다.
- `harbor` 점유층은 `road`와 별개다. 같은 해안 변의 도로와 항구는 공존한다. 항구 간 이동은 같은 층 자리 교환을 재사용하며, 건물은 이동시키지 않는다. 두 끝점은 인접하므로 정상 마을 거리 규칙을 계속 적용한다.
- 항구 표식은 변 중앙에서 **해당 육지 hex 중심→변 중앙 방향**으로 바다 쪽에 띄우고, 양 끝 꼭짓점으로 선을 잇는다. 저장 좌표는 변 ID이며 그림 픽셀은 파생값이다. 기존 프레임/SVG 여백을 넓혀 항구를 잘리지 않게 한다. 그림의 바다 배경 자체는 관측 구성물로 세지 않는다.
- `generic+3`, `Resource+2`가 기본판 일치 조합이다. 비율/종류가 모순되는 원본은 경고하며 자동 수리하지 않는다. 임의 비율을 기본판 교역 계산에 사용하지 않는다.
- 장면에 `coverageByLayer: { terrain?, numbers?, buildings?, roads?, harbors? }`를 추가하고 각 값은 `complete|partial|unknown`으로 둔다. v1은 항구 `unknown`. 기존 `coverage='full'`을 항구·말 소유권의 완전 확인으로 승격하지 않는다.
- 항구 9개 구성 검사는 해당 층을 완전히 확인했을 때의 경고다. 8개만 보인다고 남은 종류/위치를 채우지 않는다. `항구 6/9 확인 · 위치 미확인 1`처럼 실제 확인 범위를 표시한다.
- `token.variant='harbor'`의 기존 값은 종류/비율 미확인의 항구로 읽는다. 위치가 유효하면 보존하되, 사진에 없는 접점/비율을 추정하지 않는다. 의미를 보존할 수 없는 데이터는 원본 링크와 미확인 기록으로 남긴다.

### 이용 조건과 여러 항구

**RECOMMENDATION — 공식 항구 규칙을 구현한 계산식**

1. 확정 항구의 `edge.vertexIds` 중 하나에 해당 플레이어의 확정 마을/도시가 있으면 이용 가능. 도로만 닿는 경우는 제외한다. 도시는 비율을 더 낮추지 않는다.
2. 내는 자원별로 확인된 선택지 `{은행4, 일반항구3, 해당자원항구2}`를 만든다. 여러 항구는 각 자원에서 가장 작은 확인 비율을 제시한다. 비율을 곱하거나 합치지 않는다.
3. 예: 목재 2:1 + 일반 3:1이면 목재는 2, 다른 자원은 3. 목재 2:1만 있으면 양모는 4. 2:1 항구에서 얻는 자원도 그 자원으로 제한하는 오류를 피한다.
4. 한 교환 묶음은 같은 자원을 내고 다른 자원을 받는다. 예: 일반 항구에서 목재2+벽돌1을 합쳐 3:1로 계산하지 않는다. 여러 교환은 자원별로 유효한 묶음을 각각 계산한다.
5. 비율은 시설 접근 정보이고, 지금 거래할 수 있는지는 **차례·규칙 프로필·생산/도둑 처리·실제 손패·은행 재고**에 달렸다. 미확인 입력이면 가능/불가능을 확정하지 않는다.
6. 상대 항구를 직접 사용하거나, 상대 턴에 은행과 교역할 수 없다. 국내 교역은 현재 플레이어를 한쪽 당사자로 포함한다. 무료 증여·외상·개발 카드 교환을 선택지로 만들지 않는다(R6 p.7, R20 p.14, FAQ Trade).

### 실제 제공할 교역 화면

플레이어 행에는 `목재 2:1 · 나머지 3:1`과 `교역` 버튼을 둔다. 누르면 아래만 연다.

- 은행/항구 또는 플레이어 거래 선택.
- 내는 자원·수량, 받는 자원·수량, 확인된 비율과 해당 항구 강조.
- 현재 조건으로 `비율 충족`, `자원 수 미확인`, `은행 재고 미확인`, `도둑 처리 후 가능`처럼 이유를 표시. 부분 관측은 “현재 확인된 비율”로 명시.
- 저장을 위해 신규 `turn.trade`에 `{kind, playerId, counterpartyId?, harborId?, give, receive, status, given, received}`를 보관. `status`는 `proposed|in_progress|completed|cancelled`, `given/received`는 실제 전달한 수량 또는 미확인이다. 일반 거래의 내용은 공개 가능한 거래 기록이며 숨은 전체 손패를 함께 공개하지 않는다(FAQ Trade).
- 계산 버튼은 손패·은행·차례를 바꾸지 않는다. 사용자가 실물 교환 상태를 기록하고, 이미 변경된 손패가 있으면 소유자 자원 입력에서 확인한다. 재개 안내는 “받을 광석 1장 남음”처럼 남은 전달만 표시한다. 완료 거래를 다시 실행하지 않는다.

이 기능은 시설·비율 안내와 중단 상태 보존을 실제로 제공한다. 자동 거래 상대 협상, 덱 뽑기, 자동 생산·건설 처리까지 구현할 필요는 없다.

## 8. 데이터 흐름과 적용 파일

**RECOMMENDATION — 한 장면을 기준으로 연결한다.**

`원본 사진 → 항구 포함 관측 후보 → 사용자 확인/정정 → 확정 board.layout → 플레이어 공개 요약·교역비율 → 저장본 → 복원 비교`

- 원본/후보/확정값을 유지한다. 공개 점수·교역 권리는 후보를 확정값처럼 사용하지 않는다. 편집 중 미리보기는 별도 “정정 미리보기”로 표시한다.
- `board.layout`과 `components.observed`를 합계에서 동시에 세지 않는다. 부분 관측을 기준판에 반영하려면 동일 앵커·층의 명시적 반영 절차를 거친다. 카탈로그 사진의 카드들을 실제 플레이어 손패로 전환하지 않는다.
- 새 장면 v2의 `kind`, `ratio`, `coverageByLayer`는 TypeScript만 추가하면 안 된다. normalization, 모델 schema/prompt, 저장, 비교, 레거시 bridge가 모두 보존해야 한다. 현재 `version===1` 분기가 있는 곳도 함께 읽기 호환을 추가한다.
- 도둑을 옮긴 정정으로 `robber.hexAnchor`가 바뀌어도 “훔치기 완료” 같은 실제 절차는 만들지 않는다. 항구 정정도 같은 원칙이다.

## 9. 독립적인 최소 수용 예시

다음은 후속 구현 검증용 예시이며 이번 조사에서 제품 테스트를 통과했다는 뜻이 아니다.

1. **첫 화면:** 4인 판의 확인 화면을 모바일로 열면 차례/남은 처리·그림판·플레이어 요약·필요 질문에 바로 접근한다. 전체 구성물/근거 목록/JSON은 처음에 닫히며 “더 보기 +”로 접근 가능하다.
2. **미확인 손패:** 목재2, 나머지 모름이면 자원 합계2로 확정하지 않는다. 별도 확인 총수7이 있으면 공용에는7만, 소유자에게는 확인된 종류와 미확인을 구분한다.
3. **점수:** 마을2·도시1·타이틀1인 플레이어의 공개 점수는6. 비공개 승점2가 확인되면 소유자만 총8을 본다. 타이틀 보유 불명이면 정확한 공개6으로 단정하지 않는다.
4. **항구 접점:** 설명용 `r1c1.NW` 항구는 `r1c1.NW/r1c1.N` 건물에서만 접근한다. 같은 변의 도로만으로 접근하지 않으며 도로와 항구를 함께 저장할 수 있다.
5. **항구 교환:** 두 항구를 맞바꾸고 되돌리면 항구 위치만 왕복한다. 지형·숫자·도로·건물·손패·원본 사진 영역은 바뀌지 않는다.
6. **여러 항구:** 목재2:1+일반3:1이면 목재2→광석1, 양모3→곡물1을 안내한다. 목재2+벽돌1 혼합3:1, 목재항구만으로 양모2:1은 거부한다. 도시 업그레이드로1:1이 되지 않는다.
7. **보이지 않는 해안:** 지형19칸을 확인했어도 항구3개만 읽었으면 나머지6개는 자동 생성하지 않는다. 확인된 항구만 비율에 반영하고 추가 가능성은 미확인으로 남긴다.
8. **판본:** R6 행동 단계에서는 건설 후 항구 사용을 안내한다. R20 분리 모드의 건설 단계에서는 다음 자기 턴 거래까지 기다리도록 안내한다. 기존 저장본의 규칙 프로필은 보존된다.
9. **기사/7:** 굴리기 전 기사를 사용하고 도둑 이동 중 저장하면 버리기를 요구하지 않고 남은 도둑 처리 후 굴리기로 돌아간다. 7에 자원9장 중 이미2장을 버렸다면 남은2장부터 이어가며 현재7장 기준으로 재계산하지 않는다.
10. **개발 카드:** 전체 손패 기사2 중 이번 턴 구매1이면 합계는2. 다음 턴 기록 후에도 기사2가 유지된다. 새 승점은 본인 차례 승리 조건에서 예외가 되고, 사용한 기사와 미사용 기사는 합치지 않는다.
11. **거래 도중 저장:** 목재2를 건네고 광석1을 받기 전 저장하면 재개 안내는 광석1 수령이다. 계산 화면을 열거나 저장본을 복원해도 목재2를 다시 차감하지 않는다.
12. **초기 배치/잘못된 실제 판:** 둘째 거점이 첫째와 떨어져 있어도 연결 위반으로 막지 않는다. 인접 마을 등 실제 위반은 원본과 경고를 보존하며, 저장판 정정 동작을 합법적인 턴 행동으로 설명하지 않는다.
13. **타이틀/공개 범위:** 최장도로 동률에서 기존 보유자는 유지하고 과거 보유자가 미확인이면 추측하지 않는다. 공용의 브리핑·사진 대상·차이 목록에 개인 개발 카드 정체와 숨은 승점이 노출되지 않는다.
14. **호환/왕복:** v1 저장본의 판·도둑·카드 묶음을 읽을 수 있고 항구는 미확인이다. 새 항구 종류/접점/비율은 저장→재개 후 보존되며, 단순 원본 crop 변경은 배치 변경으로 표시하지 않는다.
