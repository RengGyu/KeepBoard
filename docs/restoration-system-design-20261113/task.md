1. **문제 지도:** 현재 사용자 목표의 주요 미달을 빠짐없이 분류한다. 게임 지식 부재/전달 실패, 읽기/검출/좌표, 판 인스턴스·소속·방향·끼움·겹침·순서, 여러 플레이어 영역의 전체 장면, 편집/질문/정정 재사용, 여러 사진 동일성·다른 시점, 저장·재개 일관성, 검증 자료 범위, 성능/비용을 실제 책임 경계로 나눈다. 별도 보안/인프라 사업이나 전수감사로 확장하지 않는다. 기존 해결된 것을 미구현으로 재발명하지 않는다.
2. **지식→실행 계약:** 게임팩/규칙 요약/공간·아트 정의에서 무엇을 그대로 사용하고 무엇을 추가 정형화해야 하는지 판단한다. 영역 역할, 가능한 구성/상태, 단계·판본·인원 영향, 보존할 관계를 어디에 두고 어떤 코드/모델 입력으로 전달할지 명시한다. 복원에 필요한 제약과 완전 규칙 심판을 구분한다. 공식 규칙 확인이 필요하면 1차 자료만 사용하고 링크/해당 내용/불확실성을 남긴다. 120개 게임 규칙을 무작정 전부 다시 조사하지 않는다.
3. **판독→관계→표현:** 값/검출/구조의 역할 분담, 누락판·나쁜bbox·가림 대응, 판 내부 좌표계/관계·출처·추정 가설, 물리 순서와 표시 순서, 플레이어별 상대 위치를 기존 평면 renderer에 전달하는 자료 구조와 알고리즘을 설계한다. '같은 판별 목록'과 '사진의 전체 상대 구조를 읽기 좋은 평면으로 복원'의 차이를 실제로 해결한다. 전체를 작게 축소하거나 사진 크기/원근을 그대로 복사하지 않는다.
4. **불확실성/수정:** 관측값·규칙 확인·추정·수동·미확정을 분리한다. 표시 구역 가설과 실제 판 identity를 구별해 자료가 부족해도 쓸 수 있는 복원판을 제공하는 방법을 검토한다. 잘못된 연결과 모두 미연결로 남기는 손실을 함께 다룬다. 한 번의 판/묶음 확인이 관련 대상에 전파되고 필요한 경우에만 사진/짧은 질문을 요청하도록 기존 경로를 활용한다. 수동 정정을 필수 주 흐름으로 확대하지 않는다.
5. **기술 산출물:** 현재/목표 데이터 흐름, 모듈/함수별 변경·재사용 지점, TypeScript/JSON 계약 예시, 기존 저장본 호환/버전 경계, 충돌/실패 처리, 2개 이상 대안의 장단점과 추천 근거를 담는다. 새 판독이 필요한 판단과 기존 응답/코드로 끝나는 작업을 분리한다. 기존 renderer·게임팩·저장 경계를 보강하는 설계를 우선 비교한다.

7. **구현 카드/순서:** 의존 순서, 파일/함수, 입력/출력, 소유 범위, 호환 조건, 실제 사용자 동작의 완료 기준, 필요한 검증을 갖춘 작은 구현 카드로 나눈다. 당장 할 일/후속/자료나 제품 결정이 필요한 항목을 분리한다. '프롬프트에 룰을 더 넣기'나 '가드를 완화하기'만으로 끝내지 않는다. 가장 먼저 구현할 한 묶음을 명확히 권한다.
