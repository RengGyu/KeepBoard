# 구현 후 검증 설계와 이번 확인 범위

**RECOMMENDATION — 아래 제품 검증은 아직 실행하지 않았다.** 이번 작업의 실제 확인은 기존 코드/자료/사진 열람과 metadata 집계, 설계 문서 검토다. 제품 suite·새 모델 판독·실기기 Safari를 수행하지 않았다.

## 1. 기존9응답으로 할 일과 할 수 없는 일

기존 fixture 원본과 `photo-evaluation`의 고정 대응은 그대로 읽는다. 새 결과는 별도 출력 경로에 남긴다. 현재 원장과 다른 해석은 별도 addendum/대안으로 기록하고 기존 결과를 덮지 않는다.

| 기존 입력 재생으로 확인 가능 | 추가 관측/자료 없이는 확인 불가 |
|---|---|
| 필드 간 live 물체 수집·중복/삭제 처리 | 사진 전체의 검출 recall |
| 원값/원 ID/bbox/출처/owner/native/수동 보존 | 새 숫자·색·면·방향 판독 이득 |
| current membership/부분순서 회귀 | 가려진 카드/프레임 밖 판의 실제 상태 |
| 판 없는 display region의 사실 구분 | 새 구조 protocol의 latency/비용/품질 |
| 가로 전체 구성·선택→원편집기 연결 | 다양한 새 사진/120종의 일반화 |
| 묶음 수정→저장→재열기/재개 | 실제 iPhone Safari의 제스처·메모리·시간 |

기존1430 검사는 해당 구현의 회귀 자료이고 기존363행은 같은 사진·모델 관측에 대한 대응 자료다. 이를 120종 사진 정확도나 독립 사람 정답으로 인용하지 않는다. [기존 근거](evidence.md)

## 2. 분모를 고정하고 유보를 감추지 않는다

새 사진은 가능하면 출력 보기 전에 사진을 기준으로 대상과 판단 가능성을 기록한다. 정확한 판본/부품을 아는 검토자가 확인할 수 있으면 그 출처를 남긴다. 없으면 ‘설계자 사진 판정’으로 표시한다. 모르는 것을 억지 정답으로 만들거나 사용자에게 별도 대규모 라벨링 사업을 요구하지 않는다.

| 측정 대상 | 단위/분모 | 함께 남길 상태 |
|---|---|---|
| 검출 | 사진에서 개별 실물로 판단 가능한 대상 | 맞음, 중복, 잘못 검출, 누락. 가림/겹친 group/프레임 밖은 별도 |
| 값 | 실제로 해당 속성이 보이는 matched 실물/속성 | 맞음, 오독, unreadable, wrong-face, 정답 자체 유보 |
| 기하 | 판단 가능한 실물의 visible-support/board frame | 대응 가능, 엉뚱한 위치, extent 의미 차이, 유보 |
| 판/편/역할 소속 | 실제 소속 판단 가능한 live 실물 또는 명시 group | 맞음, 오소속, 미연결, 판단유보. display-only는 실제판 정답에 더하지 않음 |
| 줄/겹침/순서 | 사전에 정한 비교 가능한 관계쌍 | 맞는 연결, 잘못 합침, 누락, 방향 오류, 비교불가 |
| 전체 상대 장면 | 관측 구역의 상대 위치/중앙/양편/이웃 edge | 보존, 뒤집힘, 누락, 경쟁. screen adjacency와 game adjacency 별도 |
| 저장/수정 | 의미 있는 사용자 transaction/복원 결과 | 성공, 일부만 반영, 참조 유실, 원값 오염, 재개 차이 |
| 가독·조작 | 실제 작업: 구역 찾기→대상 확인→필요 정정→저장/재개 | 읽을 수 있는 크기, 조작 실패/반복, 도움 필요, 사용자가 끝낼 수 있었는지 |

한 group 관측행을 개별 카드 여러 장의 성공으로 세지 않는다. 같은 실물이 여러 model run/사진에 있으면 물리 검출 분모와 observation 분모를 구분한다. 모든 관계쌍을 생성해 쉬운 음성쌍으로 점수를 부풀리지 않는다. 잘못 연결하지 않고 전부 유보한 결과도 완료 개선이라고 부르지 않는다. **오연결과 해결 가능한 미연결을 함께 보고**, 유보는 이유별로 남긴다. 새로운 정확도 숫자/고정 질문수 기준은 만들지 않는다.

## 3. 첫 구현 묶음의 의미 있는 체크

아래는 새 기능의 실제 실패를 잡는 focused checks다. 구현을 그대로 복사한 helper 단위 테스트나 반복 전체 suite를 만들지 않는다.

1. **live 전체 수집:** 여러 필드의 동일 receipt, 삭제된 board/piece, candidate/accepted 충돌, 같은 piece ID의 다른 assertion을 넣는다. current accepted entity가 주 scene에 정확히 한 번 표현되고 receipt-only 삭제물이 돌아오지 않아야 한다. private 범위는 원래 접근 정책대로 제외된다.
2. **관측/표시 분리:** Sagrada low의18개가 display grid에 있어도 window관측0/native0이 그대로다. 누락판7W 구역도 actual board count를 늘리지 않는다. 원값/owner/sourceArea/bbox digest가 변하지 않아야 한다.
3. **기존 성공 보존:** 고정 judgable 대응에서 LC baseline 연결/부분순서, Sagrada native/수동, 7W 명확한 도시/단계 연결이 퇴행하지 않는지 비교한다. 새 unlinked 해결은 원장 기준으로 실제판 연결인지 display-only인지 따로 낸다.
4. **전체 장면:** LC discard와 양편, Sagrada window/track/tools, 7W 여러 도시가 하나의 scene 안에서 찾을 수 있어야 한다. 세로 anchor목록으로 되돌아가거나 전체 축소만 제공하면 완료가 아니다. 가로 viewport에서 주사위/카드값은 읽는 크기이고 pan/jump/선택은 원편집기로 이어진다.
5. **묶음 수정→persist:** 하나의 group에 두 fields의 실물이 섞인 사례에서 판 연결을 한 번 바꾼다. 기존 명시 수동 예외는 유지한다. 재열기/명시 resume 후 같은 selected claim·대안·값·부분순서가 남아야 한다. old→new assertion map을 포함한 batch 순서 바꾸기에도 dangling ref가 없어야 한다.
6. **실패 원자성:** stale revision, 삭제 ref, 다른 scope, conflicting answer를 넣었을 때 일부만 저장하지 않는다. 같은 command 재전송은 중복 적용하지 않는다. undo는 해당 직전 수정만 되돌리고 중간의 다른 수정을 잃지 않는다.
7. **구 저장본:** sidecar 없는 retired pack/native/일반 기록을 열어 원본이 수정되지 않는지, 다음 명시 저장에서 additive state만 생기는지 확인한다. future sidecar version은 보존하며 legacy view로 읽을 수 있고 무지원 편집은 명확히 거부한다.
8. **늦은 판독/범위 재개:** group 수동 수정 후 late analysis의 구조 선택이 이를 덮지 못한다. sidecar만 바뀐 경우 유효 literal은 보존해 최신 manual 위에서 재투영하고, 값/원본 변경 때는 기존 stale 처리를 유지한다. snapshotForIntent와 일반 commit 둘 다 sidecar를 남긴다. owner resume가 public 또는 다른 owner 관계를 바꾸지 않는다. 공개 재개 뒤 원관측 epoch와 현재 captureEpoch가 달라도 유효 옛 근거는 유지된다.

T1–T4 통합 후 변경된 모듈의 기존 관련 tests와 필요한 HTTP/save round trip을 실행한다. 통합 수정으로 더 넓은 영향이 있으면 저장/판독/렌더 회귀 묶음을 한 번 확인한다. 이미 통과한 전체 suite를 근거 없이 반복하는 별도 마일스톤으로 삼지 않는다.

## 4. 새 장면의 최소 반례

정확한 장수/좌표를 코드화하지 않는 반례다. 가능한 기존 자료를 먼저 쓰고, 없으면 구현 검증 단계에서 새 촬영이 필요하다고 기록한다. 지금은 해당 새 사진을 확보·판독하지 않았다.

| 구조/실패 가설 | 최소 장면 변형 | 확인할 반증 |
|---|---|---|
| 반복 grid를 하나로 합침 | 같은색 주사위가 있는 두 개인판, 서로 다른 회전/부분가림 | board identity 분리, holes 유지, 인쇄와 실물 구별 |
| grid가 보이면 무조건 window로 확정 | 판 없는 정렬된 draft 주사위/창문 밖 도구 주사위 | display 후보는 가능하되 실판/native 확정 안 함 |
| LC 중앙선 의존 | discard가 비었거나 공용판이 잘린 양편 원정 | 근거 없을 때 A/B 유보, 양편을 한 줄로 합치지 않음 |
| 색/거리만으로 줄 연결 | 같은색의 분리된 두 줄과 사이의 떨어진 카드 | wrong merge와 해결 못 한 group을 함께 확인 |
| 겹침을 숫자순으로 오해 | 노출 방향 반대, 일부값 미독/가림, 물리적으로 비합법 줄 | 원래 부분순서 보존, legal sort 없음 |
| 누락판에서 모든 소속 포기/억지 연결 | 7W형 한 판 가림, 여러 도시, detached coins | 유용한 익명 구역과 actual membership의 분리 |
| 위치=사람/이웃이라고 오해 | 원형 자리 일부만 사진에 포함·크롭·camera180도 | owner/실제 playerCount/neighbor 추정 승격 없음 |
| 모든 back=stage | stage 아래 카드와 분리된 손/전달 카드가 함께 있음 | 끼움 근거 없는 back 역할 유보 |
| network의 화면 교차=연결 | 선로 교차/가려진 교점/같은색 말 | native edge identity와 점유 유지 |
| market의 침묵=빈칸 | 가린 칸·비어있는 칸·뒷면 더미 동시 | not-observed와 confirmed-empty 구별 |
| 멀티뷰 무조건 merge | 같은색 반복물, 다른 시점, 중간에 한 장 이동 | state/view/physical identity 별도, 합산 오염 없음 |
| 새 layer가 native를 침범 | Catan native+사진 추정, Rummikub manual group+loose | 기존 정식/수동 위치·ID·편집 유지 |

실제 새 응답에는 geometry 이상/검출 누락/역할 오독/값 오독을 나눠 기록한다. 새 decoder의 유효 ref만 처리한 성공을 사진 품질 개선과 혼동하지 않는다.

## 5. 실기기 흐름과 시간

실제 iPhone Safari에서 촬영/선택→판독→첫 유용한 값→첫 가독 scene→묶음 정정→저장→페이지 재열기→명시 재개를 연결한다. 기존 Chrome 가로 emulation은 레이아웃 참고이며 Safari 터치/줌/업로드/메모리 증거를 대체하지 않는다. 가로/세로 전환 때 같은 scene 의미와 선택을 유지해야 한다.

가로 drag가 card 선택과 충돌하는지, 긴 작업면의 panning과 page scroll이 분리되는지, 판이 큰 상태에서 옆 구역을 찾을 수 있는지 확인한다. 전체를 줄여야만 찾을 수 있거나 각 물체마다 board를 지정해야 끝나면 목표에 미달한다. 구역 한 번의 확인이 실제로 관련 물체에 전파되는지를 관찰한다. 사용자에게 매 게임의 배치법 설명을 요구하지 않는다.

시간은 전송/모델/assembly/layout/paint/저장으로 기록한다. 실패/timeout/재판독이 있으면 원래 run과 별개로 누적비용을 남긴다. 동일사진 crop 재사용과 새 외부 판독 비용을 구별한다. 응답이 짧거나 일부만 읽은 run을 더 빠른 완성 복원이라고 판정하지 않는다. 30초는 이번 선행 합격선이 아니다.

## 6. 결과 보고 형식

각 구현 카드 결과는 `변경 파일·실제 사용자 행동·검증 입력·관측 결과·미확정·다음 작업` 정도로 보고한다. 예:

> 기존9응답 재생에서 whole scene 수집/저장 회귀를 확인했다. 원관측 digest는 같다. 누락판 구역은 display-only로 표시된다. 새 검출/값 품질과 새 장면·실기기 성능은 아직 미측정이다.

이번 설계에서 검증 기록으로 남길 것은 문서 링크/계약 일관성, 원자료 manifest 대조, 제품 변경 없음이다. 이것을 후속 기능의 성공 보고로 쓰지 않는다.
