# 빠르고 쓸 만한 판 인식 — 독립 연구 (Claude, 2026-11-01)

신규 모델 호출 0 · 제품/설정 수정 0 · `.keepboard` 접근 0. 이전 Astra 권고/구현 카드 문서는 읽지 않았다.

## 결론 먼저

**지금 측정된 지연의 대부분은 "보는 시간"이 아니라 "JSON을 쓰는 시간"이다.** 기존 Terra 38회 호출에서 provider 시간은 출력 토큰 수와 거의 완전한 직선 관계다(r=0.998, 출력 1k토큰당 11.2초, 절편 2.6초, 중앙 83 tok/s). low effort에서는 출력의 85–99%가 판독 결과 JSON 자체이고, 현재 와이어는 물체 1개당 약 87토큰(중앙)을 쓴다. 같은 9개 응답을 정보 손실 없이 다시 직렬화하면 물체당 35토큰(strict schema로 쓸 수 있는 tuple 행), 22토큰(종류별 열 형식)까지 줄어든다. 측정된 직선에 대입하면 low 호출은 22–62초에서 **11–28초**로 줄어든다(추정치, 실측 아님).

**권고 흐름**

1. **촬영:** 게임팩의 촬영 영역마다 정지 사진 1장. 수동 셔터를 기본으로 하고, 자동 선별은 보조로만 쓴다. 작은 값이 많은 영역은 팩에 선언된 *다른 영역*으로 따로 찍는다. 같은 물체를 겹쳐 찍는 다각도 사진은 쓰지 않는다. 업로드는 지금처럼 촬영 중 병렬로 한다(이미 있음).
2. **판독(바꿀 곳):** 지금처럼 사진 1장당 Terra low 1회를 병렬로 보내되, 다음 두 가지를 바꾼다.
   - (a) 와이어를 **종류별 순서 고정 tuple 행**으로 바꾼다: `{"k","b":[4],"f","q","u","v":[…]}`. 값을 읽지 못한 칸은 `"~o"` 같은 사유 코드로 둔다. 이렇게 하면 `TERRA_FILL_SENTENCE`가 강제하는 null 속성 행이 사라진다.
   - (b) `stream:true`로 바꾸고 행 단위로 증분 디코드해 기존 스캔 진행 표시에 흘린다.
3. **결합/질문:** 기존 fusion과 질문 흐름을 그대로 쓴다. 독립 사진끼리는 연결하지 않는다. 현재 링크는 같은 원본 SHA 안에서만 생긴다(`shared/scanObservation.ts:23`). 그래서 영역 분할 촬영이 대응 문제를 피하는 길이다.

**이것이 현재보다 나을 근거와 한계**

- **속도(강한 근거):** 지연이 출력 토큰에 비례한다는 사실은 실측이다. OpenAI 공식 지연 가이드도 같은 원리를 적어 둔다("cutting 50% of your output tokens may cut ~50% of your latency"). 다만 줄어드는 정도는 재직렬화로 계산한 추정이다. 새 와이어에서 모델이 쓰는 토큰은 측정하지 않았다.
- **첫 결과(근거 있음, 미측정):** 스트리밍을 쓰면 첫 행은 절편(~2.6초)과 행당 ~0.4초 뒤에 도착한다. 지금은 `response.json()`으로 전체 응답을 기다린다(`server/ai/terraGameReader.ts:80`).
- **품질(가설, 미증명):** low가 물체를 놓치는 대표 사례는 다음과 같다.
  - 카르카손: 타일 2개(묶음 1개). high는 53개.
  - 사그라다: 주사위 24개. high는 43개.

  low는 물체를 묶거나 생략했다. 지금은 물체 하나를 내보낼 때마다 비어 있는 속성 행까지 써야 하므로, 물체당 비용이 줄면 low도 물체를 더 개별로 열거할 수 있다. 이것은 **가설일 뿐**이다. 반대로 와이어를 압축하면 정확도가 떨어질 수도 있다.
- **high 대체 불가:** high 지연에는 reasoning 1.5k–6.6k 토큰(18–79초)이라는 바닥이 있다. 와이어를 압축해도 카르카손 high는 약 110초로 추정된다. high는 "필요한 사진만"에 쓰는 선택지이고, 기본으로 쓰기에는 느리다.

**증명된 빠르고 좋은 해법은 아직 없다.** 속도 절감은 실측 법칙에서 나온 강한 추정이다. 품질 유지 여부는 유료 호출 없이는 알 수 없다. 다음 검증 하나가 결론을 낸다(아래).

## 가장 작은 결정적 검증 (유료 승인 필요 — 이번 권한 밖)

- **입력:** 실제 휴대폰으로 찍은 멈춘 판 3–4장면. 예: 타일 40개 이상인 카르카손, 창문판 2개인 사그라다, 티켓 투 라이드.
  - 장면마다 제품 카메라 경로의 전체 정지 사진 1장(현재 1920 영상 프레임)을 쓴다.
  - 호출 전에 사람이 직접 센 **전체 수량**(종류별 개수와 사그라다 숫자)을 동결한다. 기존 3장은 노출된 1024px 웹 이미지라 결정용으로 쓰지 않는다.
- **조건:** 같은 사진·모델·low에서 와이어만 다르게 한다. 현재 와이어 vs tuple 행 와이어(stream). tuple+high는 선택 조건이다. 장면당 1회씩, 총 8–12회, 약 $0.2.
- **측정:** 시간과 품질을 따로 잰다.
  - 시간 ① API wall, 첫 행 도착, 출력 토큰
  - 시간 ② 촬영 버튼부터 첫 편집 가능 행까지와 최종까지(capture-to-result)
  - 품질 ③ 사람 전수 대비 개별 회수, 종류 오류, 숫자 정답/오독/모름
  - 부분 AI 참조 점수와 전수 정답 점수는 따로 보고한다.
- **반박 기준:** 다음 중 하나라도 해당하면 권고를 철회한다.
  - tuple-low의 물체당 출력이 45토큰을 넘는다.
  - wall 감소가 40%에 못 미친다.
  - 현재 low보다 개별 회수가 줄거나 숫자 오독이 늘어난다.
- **결과 해석:** tuple-low가 high 수준으로 열거하면 기본값으로 채택한다. 속도만 빨라지고 열거는 그대로면, 와이어는 채택하고 열거 문제는 별도로 남긴다.
