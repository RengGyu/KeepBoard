# 최대 병렬화 재시험 — 완료

2026-10-29. 사용자 요청으로 기존 결합 설계 연구를 취소한 뒤, 실제 업로드와 같은 판독 5개를 최대2개/최대5개로 비교했다. **5개 동시 실행은 더 빨랐지만 30초 미달이며, 결합 오류도 재현됐다.** 운영 worker 수/제품 코드/모델/지시문/schema/팩은 변경하지 않았다.

## 측정

| 조건 | 판독 wall time | 입력 토큰 | 출력 토큰 | 전체 보고 토큰 |
|---|---:|---:|---:|---:|

| 5개 모두 동시 | 49.201초 | 14,509 | 20,278 | 34,787 |

각 조건1회, 실제 공급자 호출10/HTTP200·STOP10/재시도0. 같은 단위의 사진·provider 요청 body SHA 5쌍이 일치했다. 5개 조건에서는 작은 부분 사진→큰 부분 사진→전체 순으로 끝났지만 배열은 원래 unit index로 유지됐다. 모델은 Gemini 3.8 Flash, LOW, HIGH resolution, max output32768이다.

관측된 대기 차이는 약33.1%다. 단일 실행이며 출력과 개별 요청 시간이 달라 이 차이 전체를 병렬화의 안정적 효과로 확정하지 않는다. 전체 사진 요청 자체가 35.269→49.165초로 달라졌다. 입력은 같아도 응답 표현은 달랐다. 2개 조건에는 thoughtsTokenCount1645가 보고됐고, 5개 조건에는 cachedContentTokenCount3209가 보고됐다. 미보고 사고 토큰을 실제0으로 단정하지 않는다. 토큰 감소나 실제 청구액 절감으로 판정하지 않는다.

별도 업로드/입력 취득 측정:

- 사진5개 전송·등록: **45.487초**. 원본을 먼저 등록한 뒤 crop4개의 ticket/PUT를 병렬화했다. 원본 연결과 revision/CAS 보호 때문에 evidence 등록 쓰기는 순차다. 전부를 동시에 저장하면 안전하지 않다.
- 등록된 원본5개 병렬 GET 및 SHA 재확인: **11.079초**.
- 검증한 입력 bytes를 메모리에 둔 준비 처리: **0.016초**. 네트워크 준비 시간으로 해석하지 않는다.
- 단위 결과의 로컬 commit: 각각0.013/0.023초. 이 수치는 클라우드 DB 저장 시간이 아니다.

이전 순차 업로드47.718초와 이번45.487초는 다른 실행이므로 작은 차이를 최적화 효과로 확정하지 않는다. 실제 PUT 자체는0.334~2.422초였으며, ticket 발급·원본 등록 등 다른 대기가 남는다. 전체 시간의 병목이 순수 파일 전송에만 있는 것은 아니다.

5개 조건은 전체 응답에 숫자원판17·도로4·건물8이 있었다. 최종 그림에는 숫자원판7·도로4·건물2가 남았다. 기존 결합의 충돌 제외 분기로 원관측16개가 그림에서 빠지는 현상을 재현했다. raw response·관측 receipt는 보존됐고 로컬 저장·JSON 재열기 값도 같다. 따라서 저장된 원문 손실과 그림 표현 제외는 구분한다.

이전의 확실한 숫자 위치16개 기준으로 **독립 숫자원판 행만** 국소 대조하면 5개 조건은7일치/9위치없음이다. 2개 조건에는 독립 행이 없어 해당 방식으로16곳을 대응시키지 못했지만, 지형의 숫자17개는 따로 기록했다. 이를 전체 숫자 정답률0%로 해석하지 않는다. 지형 중심과 원판 중심을 정답 경계로 혼용하지 않는다. 전량 실물 GT가 없으므로 전체 정확도는 산출하지 않았다. [국소 검사](checks.json).

## 검증·범위

실제 제품 `prepareScanObservation → analyzeScanUnit → commitAnalysisTask`를 사용한 **격리 실행기**다. 모델 호출은 실제 API이며, 업로드는 운영 Supabase 경로다. 판독 실행은 Vercel durable workflow가 아니며 입력은 검증된 bytes를 메모리에 보관한다. 이번49.2초를 운영 서비스 종단 시간이라고 하지 않는다. 실제 운영 병렬 상한은2로 유지된다.

- 원사진·요청 body·응답 SHA, unit index5개, 모델 호출10개 검증.
- 집중 회귀18/18 통과. 시험 중 제품/판독 관련25파일 SHA 불변 확인.
- 단위별 원문을 private 연구 폴더에 보존. 실행 계획·사용량·출처는 [result.json](result.json).
- 자체 임시 업로드 기록만 정상 보관 처리. 사용자 기존 기록은 변경하지 않았다.
- UI·실기기 스캔·자동 분할·추가 모델·학습·배포·운영 종단30초는 이번 시험 범위가 아니다.

결론: 병렬화는 대기 감소의 후보지만 현재 최장 요청이30초를 넘고 입력/원본 등록 대기도 남는다. 우선 연구에는 **동일 실물 연결, 속성 충돌이 정상 anchor를 제거하는 현상, crop-only 관측의 추가 기준, 숫자의 중첩/독립 표현 연결**을 실제 응답과 함께 전달한다. 병렬 수가 의미 정확도를 바꿨다고 가정하지 않는다.

`single-attempt.claim`이 있으므로 `run.mts`를 자동 재실행하지 않는다. 모델 재호출 없이 `check.mts`로 저장 응답 대조를 재현할 수 있다.
