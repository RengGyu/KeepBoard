# 새 게임을 가볍게 도입하는 방법

2026-10-21. **RECOMMENDATION: 사용자는 게임 이름과 사진으로 바로 시작한다.** 내부에서는 작은 공통 팩을 자동 생성하고, 필요할 때 부품 이름·개인 구역·숫자 항목만 붙인다. 공용 판 하나와 개인 기록, 쉬운 정정, 저장한 사진/표시 그대로 보기를 공통 기능으로 만든다. 카탄의 상세 규칙/기하 편집은 기존 선택 기능으로 유지한다.

산출물: [연구 샘플 폴더](research/lightweight-game-onboarding/README.md), [입력 양식](research/lightweight-game-onboarding/profile.template.json), [오프라인 생성기](research/lightweight-game-onboarding/compile-profile.mjs), [검사 결과](research/lightweight-game-onboarding/verification.json). 제품 파일·실제 API·배포는 변경하지 않았다.

**현재 코드에서 확인한 경계 — VERIFIED**

**A/B/C 중 무엇을 먼저 할지**

| 방식 | 게임마다 작성 | 사용자에게 되는 일 | 한계/선택 시점 |
|---|---|---|---|
| **A. 사진 + 자유 영역 + 부품 목록 — 우선** | 게임 이름 1칸. 사진은 세션에 추가 | 원본 판 보기, 영역 선택/정정, 이름·수량·소유자·방향·면·부착 수정, 개인 손패/메모, 저장/재열기 | 각도/가림이 사진 그대로 남는다. 깨끗한 평면 그림으로 자동 재배치하거나 모든 각도를 하나의 좌표계로 합치는 기능은 아님 |
| B. 작은 선언형 자리 | 필요할 때 모양/행·열 또는 소수 자리 이름 추가 | 정해진 자리로 옮기기·스냅, 원본과 분리된 간단 도식 | 모든 게임 지도를 입력시키지 않음. 최소 A 검증 뒤 실제 필요가 있는 한 게임에서 추가 |
| C. 선택 전용 확장 | 카탄처럼 기하·요약을 별도 모듈에 둠 | 카탄 도로/마을 교환, 항구/교역 등 특화 조작 | 새 게임의 시작 조건으로 요구하지 않음. 공통 스캔/저장 코드는 계속 사용 |

A의 `공용 판 하나`는 **한 기록 공간**이라는 뜻이다. 대표 사진 한 장을 먼저 보여주고 보조 사진은 전환한다. 개인 사진은 각 소유자 공간에서만 표시한다. 여러 사진의 좌표가 자연스럽게 일치한다고 가정하지 않는다.

**필요 입력 / 자동 생성 / 없어도 되는 것**

```json
{ "title": "지금 기록할 게임" }
```

이것으로 유효한 기본 프로필이다. 사용자 화면에서 JSON은 보이지 않는다.

| 입력 묶음 | 작성량 | 자동 처리 |
|---|---|---|
| 게임 이름 | 필수 1개 | ID·초기 버전·3개 공통 필드 |
| 판본 | 선택 짧은 문자열 | 미기록 가능. 이름으로 판본 확정 안 함 |
| 사진 / 플레이어 | 지금 판의 사진, 개인 기록할 사람 | 기존 Evidence/ownerId/captureEpoch 사용. 게임 사전에 보관하지 않음 |
| 부품 버튼 | 선택: 이름+공통 모양, 예시는 4행 | 버튼 ID·기본 수량 모름·크롭 우선 표시. 전체 카드 목록 불필요 |
| 개인 구역 | 선택: `손패`, `비밀 목표` 같은 이름 | 소유자마다 같은 개인 장면 필드 재사용 |
| 숫자 | 선택: 이름+공용/개인/플레이어 공개, 예시는 2행 | number 필드와 간단 입력. 범위·규칙·점수 합산을 임의 생성하지 않음 |
| 공식 참조 | 선택 URL/절 또는 사용 권한이 확인된 짧은 발췌 | 출처 메타데이터. URL 입력만으로 원문 전체를 자동 수집/전송하지 않음 |

규칙 PDF, 모든 숨은 상태, 카드별 효과/아트, 모든 판 좌표, 초기 총수, 보관 체크리스트, 상세 턴 단계, 완전 복원 조건은 시작에 필요하지 않다. 소유자별 비밀 카드 내용도 그 사람이 실제 기록할 때만 입력한다.

일반 팩의 공통 필드는 `components.observed`(공용), `player.components.observed`(개인), `currentPlayer`(선택) **3개**다. 메모는 기존 `Session.notes`에 둔다. 각 개인마다 필드를 복제하지 않는다. 예시의 숫자 2개를 더하면 5필드이며 규칙/필수 질문/보관 정의는 0개다. 어느 값도 모른다고 저장을 막지 않는다.

**A에 필요한 최소 계약 — 기존 저장값 그대로 쓰기**

`GamePack`에 다음 선택 속성만 추가한다. 작성용 프로필에는 ID/kind를 요구하지 않고 공통 생성기가 만든다.

```ts
capture?: {
  version: 1;
  mode: 'photo';
  palette: { id: string; label: string;
    shape: 'piece'|'tile'|'card'|'token'|'deck';
    kind: 'unknown'|'token'|'deck' }[];
  privateAreas: { id: string; label: string }[];
}
```

장면 값은 v2를 유지한다. 게임별 임의의 `kind`를 새로 열거하지 않는다. `variant`에는 등록된 버튼 ID 또는 읽은 짧은 부품 이름을 둘 수 있다. `unknown`은 이 모드에서 카탄 종류 미지정이라는 내부 표현이므로, 화면에는 프로필 이름/원본 크롭을 먼저 보여준다. 카드의 실제 이름/구별 메모는 기존 `note`에 두며 전체 카드 사전으로 승격하지 않는다. `number`에 자원 보유 수를 끼워 넣지 않고 수량은 `quantity`, 별도 숫자는 number 필드에 둔다. photo 모드의 입력 경계에서도 `unknown/token/deck`와 `area/unplaced` 부분집합을 적용한다. 그 밖의 모델 종류는 원본/이름을 남기고 일반 부품 후보로 처리하며 카탄 숫자·위치 보정으로 바꾸지 않는다. 기존 v2 저장을 강제 재해석하는 전역 변경은 하지 않는다.

- **사진 영역:** `region`은 해당 `evidenceId` 원본의 0..1 상자다. 크롭/선택 표시는 같은 사진에서만 겹쳐 그린다. 영역 정정은 사진상의 잘못 지정된 범위를 바꾸는 동작이며 원본 사진은 그대로 남는다. 다른 사진의 영역을 대표 사진에 그대로 투영하지 않는다.
- **사진에 없는 추가 부품:** `region/evidenceId = null`, `location={type:'unplaced',id:null}`로 목록에 둔다. 사진 근거를 만들어 내지 않는다. 구역이 알려지면 `area`에 손패/더미 등의 문자열 ID를 둔다.
- **부착/방향/면:** 기존 `attachedToId/direction/face`를 재사용한다. 부착은 현재 표시 관계이고 규칙 효과·소유권 전이를 뜻하지 않는다. 이미 회전돼 찍힌 원본 크롭에 `direction`을 다시 적용하지 않는다. 90도에서 특정 상태를 단정하거나 앞/뒤를 게임의 공개/미공개 단계로 자동 해석하지 않는다.
- **수량:** `null`은 모름, 0은 직접 확인한 0. 더미의 보이지 않는 내부나 같은 물건의 다른 사진을 합산하지 않는다. 카드는 동일 모양이어도 개별 ID로 남긴다.
- **범위:** public 장면 하나와 owner 장면 하나씩. 개인 사진/부품/메모는 해당 소유자 화면에만 노출하고 공용 요약은 `visibility:'public'`인 숫자만 사용한다. 현재 owner 탭/전체 SessionView는 인증된 별도 계정의 접근통제를 증명하지 않는다. 이 설계는 그 이상의 보안을 주장하지 않는다.

B에서 사진과 분리된 도식의 이동이 필요해지면 기존 `region`을 이동 좌표로 재사용하지 않는다. 그때만 장면 v3에 `placement: {x,y}|null`(정의된 공용 도식의 정규화 좌표)를 추가하고 `capture.layout:{kind:'free'}` 또는 `{kind:'square-grid',rows,columns}`로 스냅을 계산하는 작은 확장이 가능하다. 그 도식/격자 정의는 고정된 팩에 보존하고 새 v3 reader/writer를 함께 추가한다. 같은 사진 크롭과 도식 이동 좌표를 각각 보존해야 한다. v2 → v3의 좌표는 모름부터 시작하며 이전 좌표를 추정 이주하지 않는다. 지금 양식/컴파일러는 **A만** 지원하며 B를 저장 가능한 것처럼 받아들이지 않는다. 육각 가변 지도·장소 연결 그래프·덱 내부 순서 DSL은 실제 필요 전까지 넣지 않는다.

**첫 화면과 처리 흐름**

1. `다른 게임 기록` → 이름 → `사진 추가`. 개인 기록이 필요할 때 사람/소유자를 선택한다. 부품 명세를 작성하는 화면으로 시작하지 않는다.
2. 원본 판과 인식된 부품을 함께 보여준다. 눌러 이름/수량/소유자 또는 영역을 고친다. `여러 개 선택`, `추가`, `되돌리기`는 공통 조작이다. 추가는 종류 선택 → 꼭 필요한 값 → 사진 영역 또는 목록 배치 순서다.
3. 개인 탭은 손패 사진·카드/부품·선택 숫자·짧은 메모다. 공용 판을 개인마다 새로 만들지 않는다. 공개 숫자는 공용 요약에서도 볼 수 있지만 개인 카드 내용은 넣지 않는다.
4. 누구 차례인지와 짧은 메모는 선택. `그대로 저장` → 저장 당시의 대표 사진/표시/개인 기록 재열기. 원본 없이 완벽한 실물 복원이나 완전한 규칙 진행을 보증하지 않는다.

**게임별 코드 없이 만드는 경로**

기본 경로는 `입력 → 로컬 형식 검사 → 작은 팩 컴파일 → 세션 생성`이다. AI 온보딩 요청 자체가 필요 없다. 첫 스캔에서 모르는 부품은 원본 크롭과 임시 이름으로 남길 수 있다. 게임 이름만 아는 상태에서도 기록을 시작한다.

맞춤 버튼을 원하는 경우에만 `사진/허용 참조 → AI 프로필 후보 → 같은 검사 → 이름·모양·개인 표시 범위만 사람이 정정 → 컴파일`을 사용한다. AI에게 카탄 전체 팩이나 57필드 문서를 예시로 주지 않는다. 없는 출처/판본/이용 허락은 생성하지 못하게 한다. [프롬프트 초안](research/lightweight-game-onboarding/ai-draft-prompt.md)에 경계를 명시했다.

기술적으로는 작은 JSON Schema의 `properties/required/additionalProperties`로 입력 모양을 고정할 수 있다. 생성 API의 schema 지원은 제공자/모델별 부분집합이며 형식 일치가 게임 내용의 정확성을 보장하지 않는다. 현재 `responseMimeType:application/json`/`json_object` 요청에 작은 프로필 전용 schema를 지원 API 방식으로 추가하고, 로컬 검사와 사람의 짧은 확인을 유지한다. 이 연구의 컴파일러는 새 라이브러리 없이 작은 계약만 검사한다. [JSON Schema object](https://json-schema.org/understanding-json-schema/reference/object), [Gemini structured output](https://ai.google.dev/gemini-api/docs/generate-content/structured-output)

**구현 순서와 파일 — 후속 구현자가 바로 시작할 범위**

1. **공통 기록부터 열기:** `shared/types.ts`에 위 선택 속성, 새 `shared/captureProfile.ts`에 작은 생성기. `CreateDialog`/`api.create`/`server/index.ts`에 선택 `captureProfile` 입력을 추가한다. 기존 `gamePackId` 방식은 유지한다. 서버가 이름만으로 팩을 만들어 `Session.gamePack`에 고정하면 새 게임마다 전역 라이브러리에 파일을 등록할 필요도 없다. `gamePackId`와 프로필을 동시에 보낸 경우에는 모호하게 고르지 않는다. 다음에도 쓰고 싶을 때만 기존 팩 저장 기능으로 재사용한다.
2. **사진 정정 화면 완결:** `SceneWorkspace`가 `capture.mode`로 `PhotoSceneEditor`를 고른다. 기존 `SceneEditor`는 카탄 경로로 둔다. `PhotoTargets`의 크롭/영역 표시, 기존 undo/dirty/save 처리를 재사용한다. `sceneEditing`에는 모드별 소유자 편집 허용을 추가하고 `sceneGroups`는 일반 카드/타일을 개별 표시한다. `sceneWorkspaceModel`에서 새 모드의 개인 목록/사진 범위를 분리한다. `CaptureCounters`와 `QuickContext`는 선언된 항목만 표시한다. 내부 규칙·JSON·전체 보관 질문은 새 화면에 넣지 않는다.
3. **일반 판독 연결:** `scenePrompt`/`observationPrompt`에 photo 분기를 넣고 팔레트·소유자·원본 좌표·모름만 안내한다. 일반 full-board 판정은 요구하지 않으며 공용 필드를 둘로 만들지 않는다. `normalizeObservations`/`sceneAssembly`는 동일 스캔·소유자 경계를 유지한다. 대표 사진에 없는 부품은 증거가 명확할 때만 별도 후보로 추가하고, 각도 간 대응이 불명확하면 총수를 확정하지 않는다. 기존 후보 정정과 저장 재열기를 연결한다.
4. **선택 고도화:** 공통 사진 흐름의 실제 사용에서 필요한 게임에만 B의 작은 좌표 확장 또는 C 전용 모듈을 붙인다. 특화 실패/미지원이면 사진 기록으로 계속 저장할 수 있게 한다. 카탄을 사진 모드로 자동 이전하지 않는다.

호환성: `capture` 없는 기존 팩/세션은 기존 경로를 유지한다. 새 프로필은 별도 ID와 고정된 팩 버전을 갖는다. 프로필의 버튼 순서/이름을 수정한 새 버전이 과거 스냅샷의 `variant` ID를 다시 해석하지 않게 한다. 저장값의 원본 사진, 후보, 개인 카드, 메모를 삭제하거나 이미 확정된 값으로 덮지 않는다. 연구 예시의 `capture`는 현재 validator가 무시하는 추가 속성이므로, 정식 타입/분기 구현 전 사용자에게 지원 게임으로 표시하지 않는다.
