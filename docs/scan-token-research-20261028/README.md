# 영상처럼 훑는 스캔의 프레임·호출 예산

확인일 2026-10-28. 웹·현재 공유 소스 읽기와 이 폴더 문서 작성만 수행했다. 제품/기존 설계 변경, 모델 호출, 카메라·실험 실행은 0회다. VERIFIED는 코드/문서 확인, REPORTED는 저자·기존 보고 수치, RECOMMENDATION은 제안, UNKNOWN은 미측정이다. 진행 중인 사진 묶음 구현에 추가 선행조건을 만들지 않는다.

## 권고

**사용자는 영상처럼 훑고, 기기는 작은 프레임으로 품질·중복을 검사하며, API에는 필요한 선명한 정지사진만 보낸다.** 현재 선별을 재사용하고 다음 순서로 보완한다.

1. 이미 확보한 사진 중 API에 보낼 대표 장면을 고른다. 비슷한 장면은 품질이 나은 하나를 우선하되, 가림이 달라지거나 새 영역일 가능성이 있으면 단순 중복으로 버리지 않는다.
2. 전체 기준 사진과 보충 근접 사진의 역할을 구분한다. **6장은 현재 자원 상한이지 게임마다 채울 목표나 판독 완료 기준이 아니다.** 유용한 사진이 적으면 적게 읽고, 더 필요하면 결과에서 선택적으로 이어 찍는다.
3. 호출 전 선택 사진·crop·출력 범위를 고정한다. 같은 사진의 모든 crop, 모든 프레임, 모든 미확인 속성에 자동 재호출하지 않는다.

기본 사용자 흐름은 **시작 → 훑기 → 마치기 → 자동으로 나온 그림 → 필요할 때만 정정/추가 촬영 → 저장**이다. 프레임마다 승인하거나 항목마다 정정하도록 요구하지 않는다. 이전 [설계의 감독 정정](../scan-recognition-design-20261028/README.md)을 따른다. 내부 후보/출처와 사용자 확인 버튼을 혼동하지 않는다.

## 3. 최소 선별 설계: 수집과 판독 두 단계

### A. 기기: 계속 보되 계속 저장하지 않는다

- 현재 192px/250ms 품질 검사를 먼저 유지한다. 움직임이 큰 동안 촬영하지 않고, 안정된 순간만 후보로 만든다. 250ms를 더 짧게 해서 인식 정확도가 오른다고 가정하지 않는다.
- 동일한 안정 구간 안에서는 장면이 유지되는지와 초점/반사가 개선되는지를 본다. **새 관측 가치가 없으면 추가가 아니라 대표 후보 교체** 대상으로 둔다. 첫 개선은 이미 보관된 후보의 API 선택에서 할 수 있다. JPEG를 연속으로 인코딩하는 새 버퍼를 선행 도입하지 않는다.
- 나중에 업로드도 줄일 필요가 측정되면, 업로드 전 짧은 안정 구간의 최선 후보 한 장만 확정하는 작은 대기를 검토한다. 이때 과거 작은 샘플에 고해상도 원본이 저절로 남아 있는 것은 아니다. 실제 보관할 임시 Blob과 인코딩 횟수/메모리를 함께 측정해야 한다.
- 움직였다가 다시 멈춘 구간을 별도 view 후보로 취급한다. 서로 멀리 떨어진 시점의 pHash 유사성만으로 폐기하지 않는다. 확대·반사 제거·가림 해소는 같은 실물이라도 읽을 가치가 달라진다. 반대로 카메라 움직임 자체를 새 정보의 증거로 취급하지 않는다.
- 프레임 검사 때문에 UI가 밀리는 경우에만 실제 처리 시간을 보고 샘플 간격을 늦춘다. 이는 **기기 CPU 개선**이며 API 토큰 절약과 별개다. 학습 모델을 돌려 모든 프레임의 중요도를 매기는 단계는 추가하지 않는다.

### B. 마치기: 보관한 사진 중 읽을 것만 자동 선택

기준 사진 한 장을 유지하고, 허용된 촬영 영역에서 품질을 통과한 새로운 view 또는 기존 view의 품질 개선을 더한다. 첫 전체 촬영 안내로 얻은 사진을 기준으로 삼을 수 있지만, 그것이 전체판을 담았다는 기계적 증명은 아니다. 사진 선택의 수정은 선택 기능이며 매 장 확인을 요구하지 않는다.

초기 우선순위는 **사용자가 직접 찍은/선택한 유효 사진 → 기준 사진 → 서로 다른 유용한 view → 더 선명한 보충**이다. 같은 범위의 중복은 대표 한 장을 택하되, 반사/가림이 다르면 보완 쌍을 남길 수 있다. 기준점/사진 정합이 없을 때는 ‘다양한 view를 확보’한 정도로만 해석한다.

대표 교체는 API 선택 목록의 변경이다. 이미 업로드/저장된 원본이나 사용자 기록을 삭제하지 않는다. 향후 업로드 전 후보 교체는 아직 전송하지 않은 임시 원본에만 적용하고, 전송 중인 항목을 바꿔 원본 ID와 내용이 어긋나게 하지 않는다.

커버리지는 세 단계를 섞지 않는다.

| 상태 | 의미와 처리 |
|---|---|
| 촬영됨 | 그 이미지에 픽셀이 존재한다. 선명한 값이 있다는 뜻은 아니다. |
| 판독 시도됨 | 해당 사진/영역을 API로 읽었다. 누락 없이 전부 읽었다는 뜻은 아니다. |
| 값 확인 또는 미확인 | 실제 관측값·가림·흐림·충돌을 보존. 모델이 아예 놓친 실물은 ‘모름’ 목록에도 없을 수 있다. |

확인된 사진↔판 변환이 이미 있으면 보드의 어떤 부분이 찍혔는지 도울 수 있다. 없으면 회전/이동량을 합산해 ‘판 100% 촬영’ 히트맵을 만들지 않는다. 공개/개인 scope와 같은 정지 상태 경계는 기존 묶음 계약을 유지한다. 상태가 바뀐 사진을 시간상 가깝다는 이유로 합치지 않는다.

### C. 결과 이후: 필요할 때 한 부분만 이어 찍기

연결이 확실한 결과는 기존 그림에 자동 반영한다. 불확실한 것은 ?/미배치/충돌로 남기고 그대로 저장할 수 있다. ‘반사 때문에 이 부분이 안 보입니다’처럼 출처가 있는 실패 영역만 선택적 추가 촬영 안내에 쓴다. 물체가 누락됐을 수 있으므로 원사진 보기도 유지한다.

사용자가 ‘이 부분 더 찍기’를 선택하면 그 범위/속성만 보충하고 앞서 성공한 전체판을 다시 판독하지 않는다. 모든 null을 없애려고 자동 호출 루프를 돌리지 않는다. 한 번의 추가 촬영으로 나아지지 않으면 원사진·직접 정정·그대로 저장을 남긴다. 이 선택 기능을 사진 묶음 첫 구현의 완료 조건으로 추가하지 않는다.

## 4. 호출 예산: 장수 하나로 계산하지 않는다

**초기 정책 제안:** 현재 저장 후보 상한 6을 유지한다. 그 안에서 실제 판독할 사진 수는 가변이며, 기본 1사진→1관측 단위로 시작한다. 별도 crop을 만들면 하나의 추가 단위로 예산에 포함한다. 자동으로 사진 6장×4crop을 생성하지 않는다. 초기 자동 계획의 호출 상한도 기존 최대 후보 수 6을 넘기지 않는 보수적 출발안을 권하지만, 이는 게임 완성 장수·최적값·월비용 보장이 아니다. 6까지 채워 호출하지도 않는다. 구현 중인 묶음이 여러 사진을 한 요청에 넣는다면 **요청 수와 image part 수를 별도로 센다.**

전송 전에 작은 계획 `{selectedEvidenceIds, units, imageParts, requestCap, outputCap, alreadyReadKeys}`를 고정한다. 새로운 플랫폼은 필요 없다. 같은 게임/판본·scope/owner/epoch·원본/변환 SHA·task·모델 설정의 성공 receipt만 같은 작업에서 재사용한다. 사용자 정정 후에는 과거 결과를 다시 자동 적용하지 않는다. 이미 발행한 요청의 비용을 사진 교체로 돌려받을 수 없고, 재접속/중복 finish로 같은 요청을 재발행하지 않는다. 실패도 사용한 요청 수에 포함한다.

- **로컬 샘플 수:** API 토큰 0. 카메라·화면·CPU·메모리 비용은 존재한다.
- **업로드 바이트:** JPEG 크기와 네트워크/저장 비용. 화질 압축을 높였다고 같은 비율로 이미지 토큰이 줄지는 않는다.
- **모델 입력:** 선택 image part의 해상도/모델 토큰화, crop/반복 overview/참조 이미지, 반복 prompt를 모두 포함한다.
- **모델 출력:** 종류·위치·관측 속성만 출력한다. 전체 게임 설명과 모든 미관측 필드를 반복하지 않는다. 현재 출력 상한 32768을 절약 목적으로 무작정 낮춰 잘린 응답을 만들지 않는다. 출력 길이도 실제 usage로 비교한다.
- **추가 판독/실패:** 재촬영·재호출은 별도 비용이다. 자동 retry를 늘리지 않고 기존 완료 receipt를 재사용한다.

계산은 `총 입력 = Σ(각 요청 prompt + 실제 media + 기타 입력)`, `총 출력/추론 = Σ provider가 구분한 usage`, `모델 비용 = 해당 endpoint 요율 × usage`다. provider의 total에 포함된 thoughts를 다시 더하지 않는다. 누락된 usage는 0이라고 단정하지 않는다. 정확한 토큰 사전계산이 불가능하면 이미지/요청/출력 상한은 제한하되 정확한 원화 예산 보장이라고 표시하지 않는다. 매 프레임 토큰 계수 API를 호출하는 설계는 불필요하다.

### 이미지·영상 API 수치의 주의점

2026-10-28 공식 [media-resolution 표](https://ai.google.dev/gemini-api/docs/media-resolution#token-counts)는 Gemini 3/4 이미지 LOW/HIGH 약 **280/1120**, 영상 프레임 LOW/HIGH 약 **70/280**, 오디오 **25/초**를 안내한다. 반면 [GenerateContent 영상 기술 설명](https://ai.google.dev/gemini-api/docs/generate-content/video-understanding#technical-details-about-videos)은 기본 1fps에서 **66/258**, 오디오 **32/초**를 적는다. 공식 페이지 간 차이의 원인과 현재 endpoint 실제 청구 계산은 **UNKNOWN**이다. 두 표를 섞어 절약률이나 확정 예산을 계산하지 않는다.

영상의 낮은 프레임 토큰과 고해상도 정지사진 토큰은 동등한 작은 숫자 판독 품질을 뜻하지 않는다. 영상 30fps 원본을 사진 6장과 비교해 ‘프레임 수 비율만큼 절약’이라고 하지 않는다. 서버가 이미 1fps 등으로 샘플링할 수 있기 때문이다. agentic의 공급사 장시간 영상 절약 수치도 짧은 게임판 전체 읽기에 적용하지 않는다. 현재 adapter는 이미지 GenerateContent이며 영상 입력·timestamp 출처·MEDIA_PROCESSING parts는 연결하지 않았다. 문서상 같은 API 계열에 기능이 있다는 것과 현재 앱 지원은 다르다.

## 5. 저장·업로드·기기 비용 선택

**기본은 원본 영상 미보관, 선택된 원해상도 사진과 관측 출처만 보관**을 권한다. 현재 카메라 경로와 맞고 사용자가 녹화를 끝까지 업로드할 필요도 없다. 임시 작은 샘플은 품질 선별용이며 저장·복원의 증거는 선택 사진이다. 이 선택의 대가는 버린 순간을 나중에 복구할 수 없다는 것이다. 중요한 부분이 없으면 재촬영해야 한다.

전체 영상 보관은 그 복구 가능성을 주지만 인코딩·기기 저장·업로드·서버 처리 비용이 추가된다. 기본안으로 추가하지 않는다. 개발자가 선별 성능을 시험할 때만 허용된 별도 테스트 클립을 로컬 재생 자료로 쓰는 것은 제품의 영상 업로드 기능과 구별한다. 현재 선정 사진을 먼저 업로드하고 나중에 API에서 제외하는 1단계 개선은 **모델 비용만** 줄일 수 있다. 업로드 절감은 이후 로컬 후보 확정 시점을 바꿨을 때 별도로 측정한다.

## 6. 기존 구현을 막지 않는 적용 순서

| 지금 | 진행 중 사진 묶음 job/UI | 기존 작업 계속. 추가 알고리즘·영상 endpoint를 선행 요구하지 않는다. |
| 다음 작은 개선 | `Capture` 품질 메타데이터 → `scanBatch` → `SessionWorkspace` 마치기 | `frameTime`, 품질값, 안정 구간/view 후보, `selectionReason` 정도만 전달. 보관 후보와 API 선택 목록을 구분하며 확실한 반복부터 제외. 메타데이터가 없는 기존 사진은 종전 경로 유지. |

## 7. 최소 검증안 — 실행하지 않음

우선 API 없이 허용된 짧은 실제 테스트 클립 **3개**로 현재 선별과 제안 선별을 같은 시간순 입력에서 비교한다. ①정지·천천히 이동·다른 영역, ②되돌아오기·확대·반복 무늬, ③반사/가림 변화와 중간 물체 이동을 포함한다. 판을 움직이는 예는 상태 혼합을 막는 반례다. 독립 클립 확보 여부는 UNKNOWN이며 서로 다른 정지사진을 이어붙여 실제 스캔 성능이라 하지 않는다.

- 먼저 사람이 ‘어느 구간에서 어떤 영역/작은 값이 실제로 보이는지’를 표시한다. 정답 개수·좌표를 selector에 공급하지 않는다. 값이 안 보이는 구간은 unknown이다.
- 선택 장수뿐 아니라 **유일하게 읽을 수 있었던 순간을 버렸는지**, 같은 곳의 쓸모없는 반복, 확대/가림 해소 보존, 다른 상태 섞임을 비교한다. 고정 fps를 참고군으로 넣으면 동일 최대 예산에서 비교하고 균등 표본 수를 맞춘 것을 최적화 성공으로 부르지 않는다.
- 시간순 선별은 미래 프레임을 미리 보지 않는다. 짧은 대기 후 확정하면 그 대기를 지연에 포함한다. 실제 폰에서 sample/encode/peak memory·화면 멈춤을 확인하고 카메라 실행시간을 배터리 실측으로 대신하지 않는다.
- API 품질은 이 오프라인 비교로 인증하지 않는다. 이후 기존 묶음 실사진 검증에서 고정된 선택 목록·동일 모델/task·실제 usage·판독값/누락·촬영부터 저장까지 시간을 함께 비교한다. 새 유료 실험을 이 연구에서 발행하지 않는다.
- 수용 기준은 무조건 최소 장수나 임의 정확도 %가 아니다. 읽을 수 있는 필요한 영역을 더 버리거나 사용자 재촬영/정정이 늘면 장수 감소만으로 채택하지 않는다. 실패 전송·재접속·마치기 반복으로 원본 손실/중복 호출이 없는지도 좁게 확인한다.

**미측정:** 게임별 적정 장수, 폰별 품질 임계값, 가림/coverage 자동 판정, 토큰·비용 절감률, 실제 저장까지의 시간. 이 항목은 UNKNOWN으로 남기고 사진 묶음 구현은 계속할 수 있다.
