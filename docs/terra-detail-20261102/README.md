# 모름/없음 표시 통일 · 세부 판독과 자료형 수정

모름과 정의상 명시적 없음을 스캔 결과에서 **확인 필요**로 통일했다. 저장된 false/0/null과 원응답은 구별해 보존하며, 기존 편집으로 각각 고칠 수 있다. 일반 텍스트나 의미가 다른 숫자0을 없음으로 추측하지 않는다.

## 적용한 것과 비교 후보

- **기본 v5: 자료형 손실 수정만 적용.** 모델 요청은 기존 v2와 byte-identical이다. marks 속성의 `symbol:value` 사전을 `{symbol,value}` 행으로 손실 없이 변환한다. 숫자 문자열·음수·중첩 자료·초과 행은 추측해서 살리지 않는다. 원응답과 원문 items는 그대로 남긴다. 기존 고정 v1/v2는 유지한다.
- **비교 후보 v4: 세부 판독 지침과 속성별 JSON 문법.** 특정 게임 답을 넣지 않고 작은 표식 계수, 물체 방향, 격자 칸 배열을 확인하도록 지시했다. 기존 v2와 같은 모델 low/원본 사진 high/명명 좌표/전체 속성/출력한도다. 크롭이나 새 시점 사진을 추가한 방식이 아니다. 정답과 오답이 함께 늘어 기본값으로 적용하지 않았다.
- compact v3의 좌표 구조는 이번 범위에서 수정하지 않았다. 위 v4/v5 번호는 비교와 고정 요청의 구분용이며 사용자가 고를 제품 옵션을 추가한 것은 아니다.

## 기존 사진 10장 비교

|중복 제거 사실 352개|기존 v2|자료형 수정만 (같은 응답 재생)|세부 지침 후보 v4 (새 호출)|
|---|---:|---:|---:|
|맞게 확보|311|312|324|
|오답|12|12|14|
|모름|26|25|14|
|누락|3|3|0|

**위 표는 정규화한 원관측 기준이다.** 실제 스플렌더 편집 양식은 읽지 않은 보석 색을 null로 유지한다. 확인된 비용 숫자는 보존됐지만, 남은 색이 0이라고 자동 확정하지 않아 전체 비용의 완전성은 여전히 확인 대상이다. [편집 결과의 비용 보존 검사](projected-marks-check.json)를 별도로 남겼다.

자료형 수정은 같은 원응답 10건 중 스플렌더 비용 1개만 바꿨다. 다른 값/상자/수량을 바꾸지 않았다. 이 효과는 모델을 다시 호출해서 우연히 더 잘 읽은 것과 구분된다.

v4는 10/10 정상 처리, 물체 대응 170→173/173이었다. 다만 선정 영역의 추가 반환도 3→6개로 늘었다. API 시간 중앙값은 21.63→22.68초다. 과거 v2와 새 v4 각1회 비교이므로 호출 간 변동이 섞여 있다. 사용자 촬영부터 편집 완료까지의 시간은 아니다.

## 틀린 곳이 어떻게 바뀌었나

- **주사위:** 숫자 전체 55사실에서 정답45→43, 오답6→7, 모름4→5. 사그라다의 2를1로 읽던 한 곳은 맞췄지만, 기존에 맞던 1·5를 2·4로 새로 오독했다. 일반 지침만으로 작은 숫자 문제를 해결하지 못했다.
- **조각 형태:** 블로커스의 한 Y형 조각은 이름 추측 대신 칸 배열을 맞췄다. 그러나 4칸 직선을 5칸으로 읽는 오류 등이 남았다.
- **비용:** 스플렌더 비용은 자료형 수정으로 모름→정상 배열이 됐다. 인쇄 숫자를 바꾸거나 재고/규칙으로 채운 것이 아니다.
- **작은 물체 누락:** 이전 티켓 투 라이드에서 빠진 기차 2개를 새 후보가 찾았다. 반면 추가 반환도 늘어 전체 검출 개선을 단정하지 않는다.
- **표시만 통일한 값:** 모름을 확인 필요로 표시해도 채점에서는 실제 없음(false/0 등)과 구별한다. 같은 표시를 쓴다는 이유로 모름을 정답 처리하지 않았다.

## 과적합 방지와 검증 한계

후보 요청을 동결한 뒤 한 번씩 호출했고, 같은 사진의 출력에 맞춰 지시문을 반복 수정하지 않았다. 정답표/오답 목록/재고 수량을 제품 코드에 넣지 않았다. 별도 독립 주석자가 새 보류 사진 2장과 기준표를 호출 전에 동결했고 후보 구현과 출력을 읽지 않았다.

기준은 사람 검수 정답이 아닌 AI 시각 주석이다. 이전 기준표 감사와 확실/불확실 구분을 그대로 사용했다. 블로커스·킹도미노는 붙은 조각의 총수를 확정하지 못하므로 확실한 개별 물체만 채점한다. 새 출력의 `Rows: 11,11` 등은 슬래시 bitmap과 같은 의미로 비교했다. 이 **출력 후 문법 정규화**는 별도로 공개했고 원래 문법 채점도 보존한다. 개수/정답을 고쳐 맞춘 것은 아니다.

## 최종 확인

- 신규 유료 호출14회(기존10장 후보10회 + 새2장 양쪽4회), 재시도0, 모두 형식 통과.
- 기본 v5의 실제 요청은 12장 모두 v2와 동일. 기존 원응답 재생에서는 속성4개만 자료형 정규화됐고, 기준으로 확인 가능한 비용3개의 명시된 수치를 원관측에서 복구했다. 편집 양식의 미보고 색 null은 보존해 전체 비용 확정과 구분했다. 나머지1개는 기준이 모름이므로 정답으로 세지 않았다.
- 실제 localhost 업로드→분석→저장→재개 재생26건에서 값과 원응답 보존. 구조화 비용을 편집용 고정 슬롯으로 바꾸며 추가되는 null은 별도 확인했고, 알려진 수치는 모두 유지됐다. 실제 카메라 촬영·브라우저 사용자 수정 완료까지의 시험은 아니다.
- 집중 테스트59/59, 타입검사·빌드 통과(기존 큰 번들 경고). 전체 `npm test`는905개 중881개 통과/24개 실패이며 전부 통과한 것으로 보고하지 않는다. 앞선 실행과 실패 이름이 같고 판 자산/범용 배치/기본 reader/방 UI 관련 기대 불일치가 남아 있다. 이번 범위에서 해당 변경을 덮어 고치지 않았다.

## 읽을 핵심 변경

1. `src/scanReviewValue.ts`의 표시 함수: null/정의상 없음/모름을 같은 문구로 보여주지만 저장 값은 바꾸지 않는다.
2. `server/ai/terraDetail.ts`의 `normalizeTerraDetailItems`: 사전→marks 행 변환에서 문자열 숫자·누락 수치·숨은 값을 만들지 않는다.
3. `tests/terra-detail.test.ts`: 기본 요청은 기존 v2와 같고, 원응답/0/null을 보존하며 잘못된 자료는 여전히 거절하는지 확인한다.

input → typed decoding → editable result → saved record. **원문 보존은 정답 보장이 아니다.** Terms: unknown(모름), absent(없음), lossless(손실 없음). “Keep the original value.” “The result still needs review.”
