## 권고

현재 기본 판독(기존 요청 + 자료형 손실 수정)을 유지하고, 다음 작업은 **카탄의 촬영→확인·수정→저장→실물 정리→재개·복원 흐름**을 실제 사용자 작업으로 확인하는 데 둔다. 범용 프롬프트/압축 출력의 추가 튜닝보다 실제 수정 부담과 복원 실패 원인을 먼저 확인하는 편이 이번 목표에 더 직접적이다. 이는 현재 정확도가 충분하다고 입증됐다는 결론이 아니다.

이번 조사는 문서/소스/기존 측정 재분석과 1차 출처 확인만 수행했다. 새 유료 모델 호출, 제품 수정, 배포, 중지된 구현솔2 재개는 하지 않았다.

## 왜 다음 단계인가 — 추론

1. 모델 지시문 변경의 추가 이득이 일관되지 않는다. 같은 고정 사진 반복 튜닝은 이득을 과대평가할 수 있다.
2. 제품은 처음부터 사용자의 정정과 실물 보존을 포함한다. 이미 존재하는 정정/저장 기능이 실제 작업에서 얼마나 부담을 줄이는지 아직 모른다.
3. 모름·없음은 확인 대상으로 보여도, 자신 있게 틀린 숫자는 자동으로 표시되지 않는다. 사용자가 그 오류를 발견하는지 확인해야 한다. 오독을 모름 표시로 해결했다고 간주하지 않는다.

이는 로컬 근거에서 내린 우선순위 판단이며 외부 자료가 KeepBoard의 성공을 보장하는 것은 아니다.

## 제안하는 다음 작업

카탄 기본판의 멈춘 실제 상태를 현재 앱으로 기록하고, 사용자가 결과를 고친 뒤 저장·정리·재개해서 원상태와 비교한다. 전체 사진만 보기 어렵다면 현재 지원하는 영역별 선명한 사진을 사용한다. 처음부터 큰 범용 벤치마크를 더 만들기보다 서로 다른 실제 상태 몇 회로 구체적인 실패 원인을 찾는다.

확인할 것은 세 가지뿐이다.

- **사용자가 끝낼 수 있는가:** 촬영에서 저장, 재개에서 실제 복원까지 완료되는가.
- **어디서 시간이 드는가:** 판독 대기 / 오류 찾기·수정 / 복원 시간을 분리한다. 기존30초 목표와 실제 총 작업시간을 혼동하지 않는다.
- **무슨 오류가 끝까지 남는가:** 확인 후에도 틀린 값·빠진 물체·위치/연결 오류가 남는지 본다. 단순 값 일치와 복원 성공을 구분한다.

현재 있는 결과 표시·편집·저장·재개 기능을 사용한다. 새 확인 강제 단계나 일반 보안 체크리스트를 추가하는 작업으로 확대하지 않는다. 보편 합격 정확도나 임의의 수정 허용 횟수도 새로 정하지 않는다.

## 1차 출처 조사

- [Microsoft Research — Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/): AI가 틀릴 때 사용자가 효율적으로 고칠 수 있게 하고, 불확실하면 사용자가 작업을 이어갈 경로를 제공할 것을 권고한다. 이 근거는 정정 흐름의 중요성을 뒷받침하며 현재 인식률의 합격을 뜻하지 않는다.
- [Google PAIR — Errors + Graceful Failure](https://pair.withgoogle.com/chapter/errors-failing/): 오류의 의미는 사용자 목표/기대에 따라 달라지고, 오류 후 작업을 계속할 경로가 필요하다고 설명한다. 따라서 자동 판독 사실 일치율만으로 저장·재개 제품의 성공을 판정하지 않는다.
- [OpenAI — Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices): 실제 사용 분포에 맞는 과업 평가와 사람 판단의 결합을 권고한다. 공개 사진·AI 기준표만의 반복 시험보다 실사용의 확인·수정·복원 자료가 다음 평가에 중요하다.
