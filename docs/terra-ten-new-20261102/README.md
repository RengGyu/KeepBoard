# 새 사진 10장 · Terra v2 / compact v3 비교

**결론: 현재 목표를 충족했다고 판단할 수 없다. compact v3의 일괄 전환은 보류하고 기본 v2를 유지한다.** 새 실사진 10장에 총 20회 실제 호출을 완료했으며 재시도는 0회다. v2는 10/10, v3는 3/10 정상 처리됐다. v3의 나머지 7건은 HTTP 200이었지만 좌표 형식 오류로 전체 관측이 거절됐다.

|실측 항목|기존 v2|compact v3|
|---|---:|---:|
|정상 처리|10/10|3/10|
|30초 안에 정상 결과|7/10|3/10|
|정상 결과만의 중앙 API 시간|21.63초|13.03초 (3건만)|
|저장→재개 시 값 보존|10/10|정상 3/3|

v3의 짧은 응답 시간을 전체 성공 속도 개선으로 해석하면 안 된다. 7건은 편집·저장에 쓸 수 있는 결과 자체가 없었다. 정상 13건의 저장·재개 검증은 **잘못 읽은 값도 그대로 보존할 수 있다**는 한계를 갖는다.

[사진별 시간·원본 출처](measurements.md) · [전체 원래 기준 채점](scores.json) · [좌표 실패 진단](failure-diagnostics.json) · [저장·재개 재생](save-resume.json)

실행 범위: 다른 공개 실사진 10장을 새로 검색하여, 사진당 기존 v2와 compact v3 각 1회(총 20회), 동일 Terra low/high-detail/출력 한도 32768로 비교한다. 제품 소스·기본값은 바꾸지 않는다.

사진 다운로드 원본을 그대로 입력한다. 확대·크롭 이미지는 참조자의 시각 확인에만 사용하며 모델에는 넣지 않는다. 사용자 기기 촬영 시험이나 자동 스캔 시험이 아니다. 장면별 촬영 영역을 선택하므로 전체 게임의 모든 상태를 사진 하나가 담는다는 가정은 하지 않는다.

[숫자·색·텍스트·형태·종류·위치 상세 비교](accuracy.md)에서는 사후 감사 반영 기준으로 v2 **311/352개 사실**, v3 **61/352개 사실**이 일치했다. 물체 대응은 각각 **170/173**, **44/173**이었다. 부분 사진 2장은 확실한 개별 물체만 포함하며, **이 수치를 실제 게임 전체 복원 정확도라고 부르지 않는다.**

## 비교 방법

- 각 배치의 사진·물체·보이는 값·모르는 속성을 API 호출 전에 파일과 SHA로 고정한다. root 5장과 worker 5장은 독립 준비했다. 이전 모델 출력/정답은 선택과 주석에 사용하지 않았다.
- 기준표는 AI의 시각 주석이며 사람의 검수 정답이 아니다. 전체 **명확히 보이는** 허용 종류를 목록화하고, 잘림·가림·읽기 어려움은 따로 기록한다. 불확실한 속성은 정답률 분모에서 제외한다. 확인 불가 속성에 모델이 값을 냈다고 전부 오답이라고 부르지는 않는다.
- 종류/정답값을 이용하지 않는 최대 총 IoU 일대일 대응으로 비교한다. IoU 0.25를 기본, 0.50을 민감도 비교로 제공한다. 중복 반환과 대응되지 않는 물체도 집계한다. 불확실 영역은 별도로 표시한다.
- 물체 누락/추가, 종류, 실물 단위·수량, 위치, 숫자·색·텍스트·불리언·구조화 값, 모름/생략, 표시 가능한 결과를 비교한다. 관측 색과 주사위 색 등 동일 사실의 중복 필드는 엄격한 필드 지표와 중복 제거 사실 지표로 모두 제공한다.
- API-200이어도 형식 검증에 실패하면 **실패**이며 사용 가능한 결과는 0이다. 형식 실패 사례를 정확도 분모에서 빼지 않는다. 실패한 사진을 유료 재시도하지 않는다. root 배치는 첫 형식 실패 후 멈춘 뒤 아직 호출하지 않은 항목만 이어갔다. 첫 실행 기록은 보존했다.
- root 5장 기준표에는 별도 Claude가 모델 출력을 보지 않고 사진만 재검토한다. 이것은 API 호출 후의 **사후 기준표 감사**다. 원래 사전 기준표는 바꾸지 않으며, 오류/애매함이 있으면 원래 점수와 감사 반영 점수를 분리한다. 사람 정답으로 승격하지 않는다.
- 현재 모델이 반환한 결과는 실제 localhost 업로드→분석→저장(commit)→재개(resume) 경로에도 넣는다. 이 재생은 저장된 API 응답을 대역으로 반환하므로 추가 유료 호출·키 사용이 없다. 저장·재개가 값을 보존한다는 사실과 그 값이 실제 게임 상태에 맞는지는 별개의 결론이다.

## 목표 적합성 판단

기존 30초 목표와 함께, 읽을 수 있는 복원 필요 사실이 누락/오독 없이 남는지를 확인한다. 임의로 90% 같은 합격선을 새로 만들지 않는다. 한 사진이 담지 않은 소유자·현재 차례·숨겨진 카드·덱 순서·다른 영역은 확인 불가능으로 남긴다. 전체 게임을 정리한 뒤 복원하는 목표 달성은 사진 일부의 값 정확도만으로 입증할 수 없다.

## 근거 파일

- `root-preflight.json`, `worker-preflight.json`: 사진 출처, 요청/기준표/소스 SHA, 호출 한도와 프로토콜
- `root-execution.json`, `worker-execution.json`: 실제 응답 시간·토큰·정상/실패 (재시도 0)
- `root/`, `worker/`: API 호출 전 기준표
- `scoring-protocol.json`: 정규화 규칙 및 출력 확인 뒤 변경한 채점 보완의 공개 기록
- `scores.json`: 원래 사전 기준표 기준 상세 채점
- `reference-audit.json`: 독립 사진 감사
- `failure-diagnostics.json`: 실패 원인(좌표) 분석
- `save-resume.json`: 실제 로컬 저장·재개 재생 결과


## 목표와 연결되는 실제 문제

1. **작아진 출력이 안정적인 결과를 보장하지 않는다.** v3 실패 7건 모두 좌표 순서/범위 검사를 통과하지 못했다. 일부 물체 하나의 잘못된 좌표가 전체 응답을 실패시켰다. 평가 중 좌표를 자동 수정하거나 유료 재시도해 성공으로 바꾸지 않았다.
2. **선명한 사진만으로 해결되지 않는 자료형 문제가 있다.** 스플렌더의 읽을 수 있는 비용 `white:2, red:2, black:3`을 모델은 맞게 썼지만, 비용 계약이 요구하는 marks 배열과 다른 사전 형태로 써서 제품 결과에서는 모름이 됐다. 사진 문제와 출력 계약 문제를 구분해야 한다.
3. **필요한 질문까지 이어지는지는 부족하다.** 로컬 재생 13건 모두 `questionsBeforeSave=[]`, `readyBeforeSave=true`였고 촬영 단계였다. 읽을 수 있는 속성의 모름/누락도 남아 있었다. 이 재생은 `allowIncomplete:true`, `recordingMode:'simple'`로 저장 보존을 검사했으므로 완성도 합격 시험은 아니다. 실제 촬영 완료→질문→사용자 수정까지의 브라우저 시험도 하지 않았다. 현 상태에서 필요한 확인 질문까지 자동으로 해결된다고 주장할 수 없다.
4. **복원은 물체를 찾는 것보다 요구가 많다.** 붙어 있는 조각의 형태, 개별 위치, 어느 판/소유자에 속하는지, 보이지 않는 상태가 필요하다. 이번 사진별 기하 대응은 소유자·순서·연결·게임 전체 상태의 복원 정확도를 증명하지 않는다.

## 이번 결과가 지지하는 최소 다음 수정

- 압축된 다른 필드는 유지하더라도 좌표는 이름 있는 `x/y/width/height` 같은 구조로 명확히 하고, 같은 입력에서 성공률을 다시 확인한다. 이번 측정만으로 좌표 순서 오류가 완전히 사라진다고 보장할 수는 없다.
- 비용·형태처럼 중요한 값은 속성별 자료형을 요청과 해독에서 일치시킨다.
- 복원에 필요한 값이 모름이면 해당 값만 사용자에게 확인하거나 선명한 추가 사진을 요청한다. 사진 한 장의 모든 오차를 숨긴 채 완료로 처리하지 않는다.

이 세 항목은 **제안**이며 이번 평가에서는 제품 소스를 수정하지 않았다. 기본 v2, 선택형 v3, 기존 촬영 UI를 유지했다. 키 출력·배포·커밋은 하지 않았다.
