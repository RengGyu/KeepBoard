# KeepBoard 사진 인식 방향 재평가

확인일: **2026-10-26**. 추천 연구만 수행했다. 제품·설정·기존 보고서 변경, 테스트 실행, 모델 호출, 사진 전송은 **0**이다. `VERIFIED`는 이번에 직접 읽은 코드·영수증·공식 문서로 확인한 범위, `INFERRED`는 해석, `UNKNOWN`은 미확인, `RECOMMENDATION`은 다음 행동이다. 기존 실험 수치를 새 실측이나 원본 전체 재채점으로 주장하지 않는다.

## 1. 결정

**RECOMMENDATION — 관리형 비전 API 한 번으로 보이는 구성물의 속성을 읽고, 기존 게임 정의·기하 코드로 저장 상태를 조립하는 구조를 우선한다.** Argon은 현재 가장 좋은 품질 기준점이다. 다만 과거 HIGH 전체판 요청을 그대로 기본값으로 도입하지 않고, 아래의 동일 과제 비교로 실제 사용할 모델·추론 설정을 결정한다. 싼 모델부터 자동 재호출하는 계단식 구조도 기본으로 삼지 않는다.

이유는 단순하다. 이미 관리형 모델에서 카탄 지형·숫자와 스플렌더 인쇄값을 읽은 근거가 있고, 학습 데이터나 GPU 운영을 새로 갖추지 않아도 된다. 반면 현재 가장 빠른 OCR은 전체 게임 상태를 읽은 것이 아니며, 전용 검출기를 당장 만들 판본별 실물 참조·학습 자료도 없다. **최저 호출비보다 사진 선택→검토·정정→저장까지의 총시간과 오류를 먼저 비교한다.**

지금 채택할 것은 가시 속성/위치/게임 상태의 분리, 올바른 평가 단위, 기존 후보·명시 적용·저장 경계다. **모델 기본값 전환, 자동 Atlas, 참조 검색, 파인튜닝은 보류**한다. 폐기할 것은 기존 코드가 아니라 “OCR 2/18이 숫자 정확도”, “짧게 쓰면 개선”, “재고에 맞추면 복원 성공”이라는 판단이다.

**자료의 역할:** 게임 정의는 허용 종류·필드·공개 범위·판본을 정하는 입력 문맥이다. 규칙은 읽은 값의 불일치를 표시하는 데 쓰며 가려진 값을 정답처럼 채우지 않는다. 실물 참조는 같은 판본의 그림/카드를 식별하는 별도 자료다. 현재 120정의와 표시용 SVG는 이를 대신하지 못한다. [최신 자료 목록](../hosted-vision-comparison/data/README.md)에 검증된 실물 참조셋0, 기존278사진의 원 경로0/278 존재가 기록돼 있다. 별도 보존 사본과 사용자 사진은 있으나 “278장 즉시 학습 가능”은 아니다. 텍스트 게임 문맥의 인식 효과도 **UNKNOWN**이다.

공개 구현 두 가지는 방향의 실재성을 보여줄 뿐 KeepBoard 성능 증명이 아니다. [CardLens](https://github.com/alexwing/CardLens)는 카드 검출·크롭→MobileCLIP 참조 검색→OCR로 유사 그림 구분을 수행한다. [OCR 코드](https://github.com/alexwing/CardLens/blob/main/core/recognizer/src/ocr.rs)의 이름 영역 판독도 확인했다. 참조 카탈로그가 있을 때의 방식이며, MIT 코드와 카드 이미지 권리는 별개다. 비공식·비상업 프로젝트라는 원작성자 설명을 유지한다. [Catan 전용 공개 프로젝트](https://github.com/vdakov/cv-board-game-detection)는 원근 보정→보드 검출→육각 분할→지형 분류/OCR→판 조립을 설명한다. 여러 학습 모델·데이터 준비가 필요하다. README는 확인했으나 이번 `pipeline.py` 웹 조회는 실패했고, 재사용 라이선스·독립 성능은 UNKNOWN이므로 코드를 가져오자는 권고는 아니다. 두 사례 모두 공급사 고객사 사례로 대체하지 않았다.

## 4. 위치와 상태를 어디에서 결정할 것인가

현재 OCR 요청은 `[x1,y1,…,x4,y4]` 8좌표를 요구한다. [Google 공식 이미지 문서](https://ai.google.dev/gemini-api/docs/image-understanding)의 검출 예시는 **`[ymin,xmin,ymax,xmax]`, 0…1000**이다. 문서 예시에 맞춘4좌표는 출력 부담을 줄일 후보지만 성능 보증은 아니다. 기존 감사에서 요청·원응답·정규화의 x/y 및 /1000 변환은 일치했다. **기존 두 오류를 축 교환 버그라고 고치면 안 된다.** 글자·원형 숫자 토큰·육각 타일은 크기와 중심이 다른 대상이다.

권고 흐름은 `원본/촬영 범위 → literal 관측 → 원본 근거 연결 → 위치 후보 → 사용자 정정·명시 적용 → 저장·재개`다. 모델은 종류·인쇄값·색·보이는 방향을 읽고, 불명확한 값은 null로 둔다. 소유자는 사용자가 정한 촬영 범위/색 연결에서 가져오며 사진만으로 사람이나 비공개 패를 추정하지 않는다. 수량·비용·점수는 다른 필드이고 null≠0이다.

|---|---|
| [runner.py](../../tools/hosted-vision-benchmark/runner.py) `PROMPTS`, `GEOMETRY` | 독립 비교용으로 동일 literal 과제·모델별 좌표 규약을 고정. 제품 출력 계약과 동일하다고 가정하지 않음 |

**INFERRED:** 확인된 카탄 판 기하는 LLM의 슬롯 추측보다 안정적인 연결 수단일 수 있다. 하지만 나쁜 bbox·틀린 frame을 진실로 바꾸지는 못하며, 건물 높이에 따른 시차와 자유 배치 카드에는 같은 평면 보정만으로 충분하지 않다. 위치 충돌·가림은 후보/미해결로 남긴다. 숫자 판독만으로 도로·건물·항구·손패·차례를 복원했다고 표시하지 않는다. 다른 게임은 기존 촬영 구획/정정 경로를 유지하고 검증된 공간 어댑터만 추가한다.

## 5. 대기·돈·유지 비용

**VERIFIED:** 이전 A/B 영수증은 이미지 준비 약1–2ms에 비해 provider 왕복이 전체 실험 대기의 대부분이었다. 이는 실제 사용자 업로드·대기열·검수까지의 분해가 아니다. Argon 카탄의 응답3905 + 추론9648토큰, HIGH OCR의 잘림은 추론/출력 부담을 다룰 이유다. [공식 thinking 문서](https://ai.google.dev/gemini-api/docs/generate-content/thinking.md)는 출력 한도에 생각 토큰이 포함되고, 작은 상한이 추론을 자동 절약하지 않는다고 설명한다. Argon/3.8 모두 LOW를 지원하지만 같은 LOW가 같은 계산량을 뜻하지 않으며 minimal은 지원하지 않는다.

낮은 추론·필요 속성만 출력은 **실제 대기/비용**을 줄일 후보, 진행 표시·재접속 복구는 **체감 대기/작업 손실** 개선이다. 재사용할 job·정정 UI·기하 코드는 **개발 기간**을 줄인다. 세 가지를 같은 속도 향상으로 보고하지 않는다. Qwen N1/N2 검토→저장은95.3/82.0초였으나 도구 대기가 포함되고 순서 학습 효과도 있어 실제 사용자 손작업 시간이나 개선율은 UNKNOWN이다.
