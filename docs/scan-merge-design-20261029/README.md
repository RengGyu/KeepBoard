# 전체·부분 사진 결합과 병렬 실행: 최소 수정 설계

2026-10-29 · 제품 읽기 전용 검토, 무과금 오프라인 재생. 제품·모델·프롬프트·팩·저장 schema 변경 및 API 재호출 없음. 앞선 취소 연구의 결론 대신 새 재시험의 단위 결과와 저장 장면을 직접 대조했다.

**권고: 정상 anchor를 먼저 보존하고, 물체 대응·속성 충돌·그림 배치를 따로 처리한다.** 부분 사진만의 관측은 중복 가능성을 확인한 뒤 편집 가능한 기록으로 추가한다. 위치가 불명확하면 원사진 좌표와 읽힌 값을 보존하되 보드 자리를 지어내지 않는다. 속도는 이 수정과 독립적으로, 클라우드의 묶음 대기를 없애는 변경부터 진행한다. 구체 작업과 수용 검사는 [구현 계획](implementation-plan.md)에 있다.

## 3. 일반 연결 규칙 — RECOMMENDATION

### 관측 보존과 장면 반영을 분리

1. 모든 성공 단위의 native wire, literal 관측, 원본 SHA, crop transform, 단위 ID는 보존한다. 실패 단위는 실패로 남기며 빈 성공으로 바꾸지 않는다. 투영은 복제본에서 수행한다.
2. 기존 accepted 기록과 수동값을 기준으로 삼는다. 최초 판독이면 유효한 anchor 구성물을 먼저 넣는다. 이후 부분 사진의 모순 때문에 이 객체를 삭제하지 않는다. 이는 anchor가 정답이라는 인증이 아니라 기존 편집 기록을 안정적으로 유지하는 우선순위다.
3. 기존 값이 알려져 있으면 그대로 두고 상충값을 receipt/link에 남긴다. 기존 값이 null일 때는 같은 물체의 보충 관측 중 **알려진 값들이 모두 일치하는 속성만** 채운다. `0`은 알려진 값이다. unknown/null은 0·없음·수량 1로 바꾸지 않는다. 종류가 충돌하면 종류를 임의 선택하여 결합하지 않는다.
4. 물체 대응이 모호한 그룹은 anchor/기존 객체 각각을 유지하고 crop을 미연결로 남긴다. 위치 모름과 숫자/색 모름을 분리한다. 유효한 값이 있어도 위치가 없으면 `unplaced`가 가능하다. 추가 정정이나 확인을 저장의 필수 조건으로 만들지 않는다.

### 같은 원본의 crop

- 결합 범위는 같은 plan/게임정의·field·area·scope/owner·epoch, 같은 **원본 evidence 계보와 SHA**다. 내부에서 이 범위별로 분리해 현재 연결기를 적용한다. 동일 bytes만으로 서로 다른 사진 등록/영역의 실물 동일성을 확정하지 않는다.
- crop bbox는 고정된 input/source SHA와 `sourceRegion`의 역변환으로 원본 좌표에 돌린다. 모델 bbox의 오차까지 교정된다는 뜻은 아니다. 원본 바깥/무효 bbox는 추정 확대·축소하지 않는다.
- 기존 IoU 0.75는 보수적 대응 후보 기준으로 유지한다. 이번 사진에 맞춰 임계값을 튜닝하지 않는다. 한 단위의 두 관측이 같은 연결 그룹에 들어가거나, 겹침 사슬이 여러 anchor를 묶는 경우는 대응 모호다. 가능하면 한 기준 관측에 대한 일대일 대응만 보충하며 사슬만으로 동일성을 전파하지 않는다.
- **crop-only 추가:** 같은 원본에서 기존 객체와 대응되지 않고, 같은 실물 층의 다른 관측과도 중복 가능성이 없는 그룹이면 한 편집 기록을 추가한다. 강한 일대일 중복은 한 객체로 합친다. 약한 겹침·잘린 이음새·둘 이상의 가능한 대응은 추가 개수를 추측하지 않고 raw/미연결로 보존한다. 기존 같은 종류 객체의 위치 자체가 없어 구별 불가하면 신규 추가를 보류한다.
- 수량 null/묶음은 그대로 보존하며 낱개 1개씩으로 확장하지 않는다. 자동 위치 부여는 기존 계약상 가능하고 개별 실물로 대응되는 경우에만 한다. 새 객체는 원본 evidence/region을 가진 `unplaced`를 기본으로 한다. 현재 확인 기하가 지원하지 않는 도로/건물의 자리를 생성하지 않는다. 기존 목록·원사진 보기에서 수정할 수 있다.
- 보드 자리 충돌은 객체 삭제 사유가 아니다. 기존/수동 자리는 유지하고 새 충돌 객체를 unplaced로 남긴다. 신규끼리 자리 충돌이면 모두 unplaced로 보존한다. 색·읽힌 숫자·제안 슬롯이 같다는 이유만으로 물체를 합치지 않는다.

### 지형 숫자와 독립 숫자원판

`terrain.number`는 ‘이 지형에 기록된 숫자 속성’이고, 독립 원판 bbox는 실제 원판 관측이다. 지형 중심을 원판 bbox/정답으로 대신하지 않는다.

- 초기 anchor의 inline 숫자는 그대로 보존한다. literal receipt에 해당 속성이 없더라도 native 구성물/hosted wire에서 지워 재구성하지 않는다.
- **새 판독 투영에 한해** 실제 원판 관측이 같은 원본의 정확히 한 지형 관측 안에 포함되고 다른 대응이 없을 때 부착 관계 후보로 다룬다. bbox 포함은 관계의 보수적 후보이지 검증된 실물 정답이 아니다. 숫자 값의 일치만으로 대응하지 않는다.
- 그 지형에 inline 숫자가 있고 값이 상충하거나 대응이 모호하면 inline을 유지하고 원판 관측을 raw에 남긴다. 두 개의 원판으로 추가하지 않는다. 값이 일치하거나 inline이 unknown인 경우에만 실제 관측된 원판 한 개를 투영하고 `attachedToId`로 연결한다. 이때 원판 기록을 만든 뒤 **새 투영의** inline 중복만 비운다. wire 원문은 불변이다.
- 원판에는 원판 자신의 bbox/source를 사용한다. 지형의 모델 제안 슬롯을 전달한다면 `model-proposal` 수준이며 확인 기하로 승격하지 않는다. 슬롯 충돌/불명확이면 unplaced로 남긴다. 실제 원판 관측 없이 inline 숫자로 새 bbox/실물 원판을 만들지 않는다.
- 이미 저장된 accepted/수동 inline 표현은 자동 이관하지 않는다. 관련 crop 원판은 보충 근거로 보존하되 별도 실물로 중복 삽입하거나 `componentRefs`를 지형 ID에 거짓 귀속하지 않는다. 전용 속성 링크 UI/저장 schema는 이번 범위에서 만들지 않는다.

### 다른 시점·다른 상태

다른 시점 사진은 같은 정지판이어도 crop transform으로 연결할 수 없다. 명시적 기존 실물 target 또는 이미 지원되는 사용자 확인 기하와 유일한 대응이 있을 때만 보충한다. 그 외에는 사진별 관측을 보존하고 임의 합산하지 않는다. 다른 owner/epoch/area·다른 진행 상태를 같은 판으로 합치지 않는다. 기존 [`taskTarget`/`commitAnalysisTask`](../../server/analysisTask.ts)의 범위·수정 revision·원본·PIN/권한 재검사와 최종 1회 반영을 유지한다.

## 4. 속도 개선 순서와 한계

**측정 사실:** 업로드·등록 45.487초, 병렬 GET+SHA 11.079초, 메모리 준비 0.016초, 로컬 commit 0.013/0.023초였다. 서로 다른 계층의 수치이므로 운영 한 요청의 종단 분해처럼 합산하지 않는다. PUT 자체는 짧았지만 ticket/등록/응답 중 어느 부분이 나머지 대기를 지배하는지는 아직 미측정이다.

1. **동시 상한을 늘리기 전에 cloud 대기 제거.** [`analyzeScan`](../../server/scanObservation.ts)은 빈 자리에 다음 요청을 넣는 2-worker 방식이다. [`analyzeWorkflow`](../../workflows/analyze.ts)는 2개 전부 완료를 기다리는 wave 방식이다. cloud도 2개 상한 내 rolling dispatch로 맞춘다. 단위별 claim·retry 0·원래 index 저장·모든 실행 중 작업 종료 후 commit/release를 유지한다. 이번 cap2 실측은 rolling 실행기이므로 cloud 수정의 실측 개선값은 아직 없다.
2. **업로드는 전송과 등록을 분리.** [`api.evidence`](../../src/api.ts)의 ticket→PUT→등록을 모두 동시에 호출하지 않는다. 원본 등록을 먼저 완료하고, 독립 ticket/PUT는 작은 상한 2로 겹치되 evidence 등록과 SessionView/revision 반영은 원래 index로 순차 처리한다. 기존 [`createScanUploadQueue`](../../src/scanUploads.ts)의 bytes/실패 보존을 유지한다. 등록 응답을 기다리며 다음 독립 전송을 준비할 수 있지만 분석 plan은 선택 사진 등록 후 고정한다. 이번 시험이 이미 일부 병렬 전송을 했어도 45.5초였으므로 이 변경만으로 큰 개선을 보장하지 않는다. 단계별 시간 기록을 함께 비교한다.
3. **5동시 기본 적용은 보류.** 현재 [`CloudJobs.slot`](../../server/cloudJobs.ts)은 단위가 아닌 job 2개를 허용한다. per-job 5로 바꾸면 최대 10호출이 된다. 우선 2×2 상한을 유지한다. local 상한은 프로세스, cloud 상한은 저장소 namespace 범위이며 계정 전체의 전역 한도가 아니다. Vercel/공급자의 현재 계정 동시 한도는 UNKNOWN이다. 새 큐 없이 상한을 보장할 수 있는 별도 근거가 생길 때 확대를 판단한다.

단위 시작 전 job lease를 갱신하고, lease가 만료되어 다른 job이 들어오는 동안 이전 요청이 계속 실행되는 상황을 검사한다. 현재 lease 5분·provider timeout 180초를 네트워크/저장 대기와 구별한다. slot을 얻지 못하면 호출하지 않는다. 클라이언트 timeout 이후 공급자 실행이 즉시 중단됐다고 가정하지 않는다. durable 재전달은 완료 결과 재사용 또는 interrupted이며 자동 유료 재송신하지 않는다.

**30초는 목표이지 보장이 아니다.** 이번 전체사진 요청만 35.269/49.165초였다. 병렬 수 확대만으로 최장 단위보다 빨리 최종 결합할 수 없다. 출력량/모델/작업 변경은 별도 비교가 필요하며 이번 최소 제품 수정에 섞지 않는다. 병렬화는 wall time을 줄일 가능성이 있지만 토큰 합이나 원가를 자동으로 줄이지 않는다.

## 5. 남은 UNKNOWN과 사용자 설명

실물 전량 GT, crop-only의 실제 중복 여부, 다른 사진/게임으로의 정확도 일반화, 새 결합 후 실화면·운영 종단 시간은 미확인이다. source transform의 계산 정확성과 모델이 상자를 올바른 실물에 그렸는지도 별개다. 새로운 저장 schema나 팩 판본 변경은 이 최소안의 선행 조건이 아니다.

사용자에게는 **“부분 사진이 다르게 읽혔다는 이유로 전체 사진의 정상 말까지 사라지지 않게 합니다. 추가로 읽힌 물체는 중복을 구분해 남기고, 자리가 불분명해도 사진과 값은 저장합니다. 병렬 처리의 대기는 줄이되 30초 완료는 아직 확인하지 못했습니다.”**라고 설명할 수 있다.
