아래 본문을 전달하고, 비공개 GitHub 연결에서 해당 브랜치를 선택하거나 해당 커밋의 저장소 ZIP을 첨부한다. 이 의뢰는 Pro에게 직접 분석·연구·설계를 요청하는 것이며, 로컬 구현을 이미 수행했다는 뜻은 아니다.

KeepBoard의 실제 코드와 사진/판독 결과를 검토해서 **남은 위치 복원·판독 문제의 수정 방향과 구현 가능한 설계**를 만들어 주세요. 어려운 시각 분석, 정답표 작성, 구조 알고리즘과 모델/판독 전략 연구는 당신이 직접 수행하고, 구현자에게 넘길 구체적인 결과물까지 주세요. 단순 체크리스트나 “에이전트에게 조사시키세요”로 끝내지 마세요.

## 목표와 현재 우선순위

게임을 사진으로 기록한 뒤, 읽기 쉬운 평면 그림과 사진·차례·메모로 실물을 다시 펼쳐 게임을 이어갈 수 있어야 합니다. 필요한 것은 단순 색/숫자 목록이 아니라 **올바른 칸·편·소속 묶음·순서·연결과 필요한 겹침 관계**입니다. 사진 원근/작은 크기를 그대로 복제하지 말고, 실제 관계를 유지한 읽기 쉬운 판이어야 합니다.

장기 목표는 현 120종과 향후 확장입니다. 이번에는 게임 수를 늘리지 말고 현재 3종에서 발견된 실패를 해결할 공통 원리를 세워 주세요. 사용자가 게임마다 배치 방법을 하나씩 설명하게 만들지 마세요. 현재 게임팩·보드·아트·정정·저장·재개 경로를 재사용해야 합니다.

**30초에 집착하지 않습니다.** 위치와 필요한 정보가 맞는지가 먼저입니다. 품질·누락·복원 가능성을 함께 보고 모델 강도/속도/비용을 판단해 주세요. 5~10%는 사용자 오답 허용 방향이며 현재 달성 수치가 아닙니다. 임의의 새 성능 목표나 방대한 전수 검사를 선행 과제로 추가하지 마세요.

추정 배치는 허용합니다. 추정/수동/정식 위치/원관측을 구분하고 편집 가능해야 합니다. 모름·미배치를 숨기거나 원 ID·값·geometry·사용자 수정·판본/소유 범위를 덮지 마세요. 사람/모델이 볼 수 없는 숨은 값을 만들어 넣거나 불필요한 더미 아래 개별 카드까지 읽으려 하지 마세요.

## 읽는 순서

1. `USER_GOALS.md`, `OPUS_REVIEW.md`, `EVIDENCE.md`, `SOURCE_MAP.md`.
2. `shared/estimatedBoardStructure.ts`, `shared/estimatedGeometry.ts`, `shared/drawingProjection.ts`의 실제 흐름.
3. `src/GameBoardRecord.tsx`, `src/EstimatedBoardView.tsx`, `src/GenericPieceArt.tsx` 등 실제 표시/정정 경로.
4. 같은 폴더의 `photos/`, `screenshots/`, `data/cases/`, `data/structures/`를 서로 대조.
5. 필요하면 `server/ai/`의 실제 요청/decoder·assembly·fusion, 저장 intent/재개 경로를 따라가 주세요.

오푸스 검토의 결론을 그대로 승인할 필요는 없습니다. 원사진과 코드로 직접 확인해 동의/반박/보류를 구분해 주세요. 기존 AI 정답 초안도 권위 있는 정답이 아닙니다.

## 당신이 직접 해결해서 반환할 내용

**1. 위치 복원 감사와 원인 판정 — 최우선**

- 사그라다: 창문 18칸 외 트랙 자리/도구·목표/토큰 연결, 다른 응답의 판 누락·역할 오분류·방향/원근 가정까지 확인해 주세요.
- 로스트 시티: 전체 양편·5색줄·버림 역할·줄 안 순서를 대조해 주세요. 기존 41/42는 정답 수가 아닙니다. 6/9 오독과 중복/추가 실물을 위치 문제와 분리해 주세요.
- 세븐 원더스: 101/117 묶음이 맞는지 원사진 대조를 직접 하세요. 최소20개 표본은 판별/색별로 치우치지 않게 선정하고 선택 방식·piece ID·bbox·현재 anchor·사진상 anchor·정답/오류/판정불가와 근거를 표로 주세요. 가능하면 제공 사진의 나머지도 확인해 주세요. 사람 소유 추정과 판 인스턴스 묶음은 구분해야 합니다.
- 원인 층을 물체 검출 / 값 인식 / source-area 역할 / bbox / 구조 변환 / 검증·조립 / 표시 / 저장·재개로 분리하고 정확한 파일·함수·조건을 제시해 주세요. 고칠 필요가 없는 기존 구현도 짚어 주세요.

**2. 공정한 정답표와 응답 대응 수정**

기존 high/medium/low6건에서 응답 ID가 달라도 같은 실물을 대응시켜 다시 평가하세요. IoU·중심거리·일대일 대응·유형·색 alias·구조 맥락을 어떻게 사용할지 결정하고 실제 표를 만들어 주세요. **색을 강제 일치 조건으로 삼아 색 오독을 채점에서 빠뜨리지 마세요.** 겹친 카드·하나의 넓은 bbox가 여러 실물을 포함하는 경우·중복 검출·짝이 모호한 경우를 남기세요. 미대응을 오독으로 계산하지 마세요.

사그라다 창문18칸은 원사진 기준 표를 직접 작성하고 근거와 판정 불가를 남겨 주세요. LC는 9→6과 추가8이 실제로 어떤 실물에 대응하는지 확인해 주세요. 읽을 수 없는 값은 정답표에서도 유보합니다. 게임/영역별로 값 오독·모름·검출 누락/추가·위치 오류·미배치의 분모를 나눠 보고하고, 전체 오답률을 계산할 수 없다면 왜 그런지 명시해 주세요.

**3. 범용 위치 복원 설계**

현재 팩/보드 정보를 사용해 격자, 양편 색줄, 플레이어별 tableau, 지도/노선, 더미/부착처럼 관계가 다른 구조를 어떻게 공통 처리할지 설계해 주세요. 현3종에 숫자를 박아 맞추는 설계나 새로운 별도 렌더러는 피하세요. 어떤 정보는 모델이 읽고, 어떤 관계는 코드가 계산하며, 어떤 불확실성은 사용자 한 번의 정정으로 해결할지 명확히 하세요.

가림·회전·대각선·원근·여러 판·판 anchor 누락·불분명한 owner·이동/삭제·저장 재열기에서 구조를 잘못 확정하지 않는 기준을 주세요. 사진 줄과 실제 게임 묶음이 다른 경우도 다뤄 주세요. 원문·값·좌표를 보존하는 자료형/우선순위, 수동 override 저장 계약, 실패 시 화면 동작, 최소 변경 파일/함수와 유효한 정답 fixture를 포함해 주세요.

**4. 필요한 판독 범위·의심 표시·모델 선택**

숨은 값/불필요한 이름/뒷면 속성을 묻지 않으면서 복원에 필요한 수량·순서·역할을 잃지 않는 기준을 제시해 주세요. 게임 규칙은 의심 표시를 위한 보조 근거로 사용하고 자동으로 숫자/위치를 고치지 마세요. LC의 중복·오름차순·6/9, Sagrada의 눈 범위·칸 상한을 검토하되 규칙만으로 추가 카드/위치 정답을 증명했다고 하지 마세요. 규칙에 판본 차이/예외가 있으면 공식 규칙 자료를 확인하고 링크를 주세요.

medium이 채점기 문제로 과소평가됐는지 직접 판정하고, high/medium의 값·위치·누락·시간/비용을 공정하게 비교하세요. 30초 통과를 기본 강도 전환의 필수 조건으로 두지 마세요. 기존 자료로 결론이 안 나면 필요한 최소 추가 실험의 가설·변수·입력·호출 수·비용·선택 기준만 제시하세요. 키를 요구하거나 임의로 유료 API를 호출하지 마세요.

**5. 실제 화면과 지원 수준**

넓은 화면의 반복 빈 라벨을 모바일처럼 간결하게 만들 최소 변경을 주세요. 구조 관계/원사진 연결/정정 동작을 유지하세요. 세븐 원더스는 현재 카드명3/86 수준을 솔직히 다루되, 이름·색·수량·묶음 중 재개에 꼭 필요한 항목과 아직 부족한 항목을 구분해 주세요. 사용자 동의 없이 제품 범위를 사진 보관/4종 한정으로 축소하지 마세요.

## 최종 결과물 형태

가능하면 아래를 다운로드 가능한 Markdown/CSV/JSON 및 실행 가능한 분석 코드로 함께 반환해 주세요. 사용자가 결론을 반복해서 물어보거나 로컬 구현자가 다시 연구해야 하는 상태로 끝내지 마세요.

1. `README.md`: 무엇을 직접 확인했는지, 최우선 결함과 추천 순서, 미확인 사항. 코드 SHA 명시.
2. `placement-audit.csv` + 이미지 근거: 원사진의 실물과 현재 칸/편/묶음/순서를 연결한 판정, 특히7W 표본20.
3. `ground-truth.json`, `matched-results.csv`, `metrics.json`: 사진 기반 정답/유보, 기존6응답 재대응 결과와 분모. 근거가 부족한 항목은 추정으로 표시.
4. `design.md`: 범용 구조·데이터 계약·현재 구현 재사용·실패 경계·게임별 필요한 정보·모델 선택 근거.
5. `implementation-plan.md`: 우선순위별 작업 카드, 수정 파일·함수·계약·완료 조건·필요한 직접 검사. 가능하면 최소 patch/실행 가능한 함수·재현 예제까지.
6. `experiments.md`: 기존 근거로 해결한 것과 추가 사진/호출이 꼭 필요한 것을 분리. 새 호출이 필요 없으면 없다고 명시.

현재 코드에서 잘 된 부분은 보존하고, 위치 정확도부터 해결할 가장 작은 일관된 변경안을 추천해 주세요. 기존 수치를 반복하거나 일반론/검증기 문구 조정만으로 완료하지 마세요. 코드를 실행했는지, 사진을 직접 보았는지, 연구만 한 부분인지를 구분해서 보고해 주세요.
