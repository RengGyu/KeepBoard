# 스캔 사진 병렬화 — 채택 설계

2026-10-29 감독 작성. 기존 아스트라 검토 중단 기록과 현 소스를 바탕으로 최소 범위를 채택했다. 아스트라 Ultra와 구현솔 High 세션은 재개 후 429로 다시 중단됐으므로 **아스트라의 최종 승인 문서가 아니다.** 구현·검증은 감독이 직접 수행했다.

- 로컬: 스캔 작업당 worker 2개. 완료 순서와 관계없이 고정 unit index에 결과를 넣는다. 마지막에 기존 projection/commit을 한 번 수행한다.
- 클라우드: 스캔만 최대 2개씩 wave로 실행한다. 일반 분석은 순차를 유지한다. 각 wave 전에 기존 job lease를 확보·갱신한다. 기존 2 job 슬롯과 합쳐 같은 namespace의 유효 lease 아래 정상 진행 호출은 최대 4개다. 로컬도 한 프로세스의 기존 2 job 제한 아래 최대 4개다. 서로 다른 프로세스/namespace 전체를 묶는 보편적 제한은 아니다.
- wave는 `Promise.allSettled`로 모두 끝난 뒤 실패 정리한다. 빠른 실패 하나 때문에 아직 실행 중인 다른 호출의 job lease를 조기에 풀지 않는다.
- 기존 `claimBatch`의 create-only CAS를 호출 전에 유지한다. completed는 재사용하고 started는 재호출하지 않는다. 모델 step 자동 재시도는 0이다. 연결 단절 후 공급자가 계속 처리하는 경우의 중복 과금을 막기 위해 자동 재시도하지 않는다.
- 단위별 원사진·입력 SHA·영역·변환·원응답을 유지한다. 같은 값이나 색이라는 이유로 다른 사진의 실물을 합치지 않는다. 기존 연결·충돌·미배치·수동값 보존 규칙은 바꾸지 않는다.
- 일부 판독 실패는 해당 단위 상태로 보존하고 나머지는 기존 경로로 저장한다. 최종 commit에서 epoch/영역/revision을 다시 검사한다.
- 스캔 단위의 모델 소요 시간을 기존 cloud timing 기록에 전달한다. `providerMs` 합계는 병렬 wall time이 아니다.

검증: 순서 역전, source SHA 유지, 부분 실패, cloud 동시 실행·완료 후 재전달, CAS claim, lease 제한·반환, 수동값·null/0·저장 재열기, 실제 workflow 본문의 2개 wave와 실패 join을 검사한다. Workflow durable runtime 자체의 운영 검증은 별도이며 로컬 step 대역 검사와 Vercel 빌드로 혼동하지 않는다.

실사진 비교는 같은 바이트의 4개 요청을 cap1/cap2로 각각 1회만 실행한다. 이전 임시 원본이 사라져 보존된 공개 사진 목록의 다른 카탄 원본을 다시 확보했다. 기존 원본 성능의 재현 또는 정확도 인증으로 주장하지 않는다. 영상/추가 촬영 UI/자동 모델 선택/배포는 이번 구현에서 제외한다.
